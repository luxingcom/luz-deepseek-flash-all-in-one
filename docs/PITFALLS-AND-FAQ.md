## 卷首一：定性四律（排任何问题前先读这四条）

这四条贯穿两本手册的全部事故复盘，也是本词典排序与取舍的依据。违反任何一条，
后面所有命令跑得再对，结论也会反。

1. **先认代际，再对表。** 本仓与上游常同时保留两代档案（例如环网形与交换机形、
   0.3.1 基底与 0.3.2 增量），同一个键在两代里值不同。拿旧一代的表去判新一代的站，
   会把"我们做对了"判成"我们偏了"，然后按"照规范改回来"的建议把性能砍掉一半。
   动手对表之前，先确认手上这张表是哪一代、哪个形态的（详见 P8-5）。
2. **形面只是上半场，必须打真请求。** env 键逐字对上、启动参数齐、横幅正常、
   四机面指纹全等，只证明"配置长对了"，不证明"功能合同是好的"。实测出现过形面
   全绿、一带 `tools` 的真请求就暴出 P0 的事故（详见 P8-1）。
3. **先查配置，后动硬件。** 配置偏差改一个键就回去了；物理改动（换线、对调、
   重布线）代价最高且不可逆。任何"先动硬件再回头查配置"的顺序都是错的（详见
   P8-7）。同理：先查自己加的键，再怀疑厂商件；先查软件面，再怀疑线材。
4. **负结论写穷尽范围。** 报"没找到/没发/没有方案"时必须写清查过了哪几处
   （远端 tag 面、镜像内、兄弟仓、已删历史……），否则别人无法复核、也无法判断
   你漏了哪一处。报不出的量就不给数字，没核实过的差值不要报为成绩
   （详见 P8-4、P8-6、P5-16）。

## 卷首二：占位符表

本词典**不出现任何真实内网 IP、主机名、registry 地址、家目录路径**。命令里的
站点专属值一律用占位符，按自己环境替换：

| 占位符 | 含义 | 示例/说明 |
|---|---|---|
| `<H1>` ~ `<H4>` | 四机地址，rank0~rank3，`<H1>` 为 head | 排障命令默认在 `<H1>` 上执行 |
| `<USER>` | 登录用户 | |
| `<PORT>` | 引擎监听口 | 示例值 8899（按站点替换） |
| `<GW_PORT>` | 网关/并发代理口 | 与引擎口不同，别混用 |
| `<CTN>` | 引擎容器名 | head 与 worker 容器名不同，分别替换 |
| `<ENVFILE>` | 站点形 env 文件路径 | 如本仓 `deploy/env/` 下各形落位后的文件 |
| `<IM_*>` | 镜像（`<IM_OLD>` 旧代 / `<IM_NEW>` 新代 / `<IM_A>`、`<IM_B>` 待比对的两个） | |
| `<BOOT>` | 点火脚本 | 本仓对应 `tools/boot-with-slotlock.sh` 包裹的 boot 件 |
| `<IFACE>` | 网卡口名（RoCE 口） | 逐口执行时替换 |
| `<PREFIX>` | 容器名前缀 | 停栈断言用；注意脚本默认前缀可能与你产线不同 |
| `<PRODUCT_DIR>` | 站点部署资产目录 | adapter 位、overlay 位、bin 位等所在根 |
| `<对端IP>` / `<邻居>` | 路由验收中的对向地址 / 该口邻居地址 | |

注意两点：

- 占位符示例值不必与仓内正档的示例一致。仓内档（如 `UPGRADE-0.3.2.md` §10）
  自带自己的示例口与路径；**引用仓内档命令时按其原文执行**，别把本词典的示例值
  混抄进去。
- 手册原文已脱敏（产品代号写 `<LIB>_*`、`<MK>_*` 等），本词典保持同款口径；
  引用仓内公开档时直接使用仓内公开键名（如 `B12X_ROCE_PEER_HCA_MAPS`）。

## 卷首三：本词典用法

每个条目固定四段，方便按需跳读：

- **现象**——报错原文或读数照抄，是你最先看到的东西；
- **根因**——一两句讲清背后机理；
- **判据**——可复制执行的命令与期望输出，用来确认"是不是这个坑"；
- **处置**——具体动作，并明确"别做什么"（错误动作常常比不动作更贵）。

中文为主；命令、字段名、报错原文保留英文。引用仓内档一律给相对路径（如
`UPGRADE-0.3.2.md` §5）。文末有两张表：**症状关键字索引**（关键字→条目号，
便于 grep）与**手册条目→本文条目对照表**（证明手册无条目丢失）。

## 卷首四：坑的分层地图（本词典十章）

从下往上排障，绝大多数误判发生在"用上一层的结论去解释下一层的现象"：

# 一、物理与网络面

这一层是地基：接线、网卡口、路由、织网转发规则。这一层的结论最容易污染上面
所有层——很多"引擎慢/引擎挂了"最终查明是这里的规则没落地。

## P1-1 对向两跳通路：中间机硬件转发，织网黄金态 = 每机恰 2 条 in_hw

**现象**：起栈后在图捕获阶段报
```
RoCE proxy failed: RDMA write to rank N path 0 failed:
transport retry counter exceeded (vendor_err 0x81, seq 1)
```
其中 N 恰为本机的**对向** rank（4 机环里 rank0↔rank2、rank1↔rank3）。

**根因**：4 节点环里，对向两台之间**没有物理直连链路**。对向数据靠中间两台机器的
网卡硬件转发：对向 QP 带 flow label 16383，mlx5 驱动由此派生 UDP 源端口 65535，
中间机按端口匹配后只改以太头、从另一个口转出。转发规则由织网工具（mesh/fabric
一族）铺设；规则不存在、或没有落到硬件上，对向通路必挂。引擎侧只调标准 verbs
（create_qp / modify_qp / reg_mr / post_send / poll_cq），**零 flow steering**——
它假设硬件转发规则已经存在，不会自己补。

**判据**：织网的门禁判据是"每机 2 个 transit 口、每个口恰 1 条 `in_hw` 的
tc flower 规则"，不是"有规则就算"：

```bash
for d in $(ls /sys/class/net | grep -E '^en'); do
  printf '%s in_hw=%s\n' "$d" "$(tc filter show dev "$d" ingress | grep -c in_hw)"
done
systemctl list-units --all | grep -Ei 'mesh|fabric'
```

期望：每机合计恰 2 条 `in_hw=1`。`in_hw=0`（软件落地）等于没装，是 fail-closed。
规则形（由织网工具铺设，供识别用，不建议手搓）：

```
tc filter add dev <IFACE> ingress protocol 0x88b5 pref 49159 handle 49159 flower skip_sw \
  src_mac <邻居> dst_mac <对角> action pedit ex munge eth type set 0x0800 pipe \
  action pedit ex munge eth dst set <本机> pipe action mirred egress redirect dev <另一口>
```

**处置**：用织网工具重织并复验 `in_hw` 计数。装载件（检查/自愈/自检、拓扑生成器、
mesh-up/mesh-down、hairpin/qos、systemd 双单元、topology 描述件）通常**不在交付包
里**，在同作者的基础设施/兄弟仓——交付包里 grep 不到时先读交付仓 README 的
"基础设施仓 / 上游 / 致谢"指引段，别判成"厂商没做"。两个"别做"：①别自己用
netdev `tc` 重实现拦截——发往 4791 的 RoCE 流量在网卡内部先被 RDMA steering
接走，不进 tc 域，必须用 `skip_sw` 的 flower 规则；②别把 `OPPOSITE_PATHS` 当
调参去改——它设 2 或 4 时上述报错逐字同形，改它白费一轮（见 P4-3）。另外，
停/启织网必须走 systemd unit，**别 pkill**——残留流表会把 TX 吞吐塌到 ~14Gb/s
量级（同族症状见
`tools/packages/fabric-net/payload/runbook/COMMUNITY-FIELDNOTES.md` 症状 3）。

## P1-2 织没织网的另一读数：RoCE cap 值与装载顺序

**现象**：拓扑生成器算出的 RoCE cap 是 `81920`；或 qos 相关参数看着没生效。

**根因**：cap=81920 对应 hairpin 队列缺省档（1024 量级），是"**还没织网**"的指纹，
不是可调优参数；织网后的形是 262144 量级（hairpin 大队列档）。另外有一条硬顺序：
qos 脚本必须**后于** hairpin 脚本执行——hairpin 的 `devlink driver_reinit` 会把
trust 模式打回 dscp，把先铺的 qos 冲掉。

**判据**：看生成器输出的 cap 值；看两个脚本的实际执行顺序（`journalctl -u <单元>`
的时间轴，qos 的事件时间必须晚于 hairpin）。

**处置**：重新织网拿到 262144 量级 cap；固定 qos 后于 hairpin 的顺序。别把 81920
当作"可接受的低配"继续起栈——它意味着转发面根本没织好。

## P1-3 `PEER_HCA_MAPS` 是属主映射表，照抄必挂

**现象**：直接照抄交付包 env 里的映射表，起栈报
```
RoCE all-reduce connect failed: rank 0: RoCE queue-pair connect failed:
ibv_modify_qp(RTR): Connection timed out;  rank 2: …同
```
报错**点名具体 rank**。

**根因**：这张表（本仓公开键名 `B12X_ROCE_PEER_HCA_MAPS`）编码的是**作者站点的
物理接线**——哪个节点的哪个口连哪两个对端。你的接线与作者不同，照抄即错；而且
错在哪几段，报错就点名哪几个 rank，因果是一一对应的。

**判据**：把交付形与本机实测值**按 rank 段逐段 diff**（表用 `;` 分隔，段顺序即
rank 顺序）。不一致的那几段，就是报错点名的那几个 rank——因果吻合即可高置信
动手，不用先去查网卡：

```bash
# 取容器内实际生效值并按 rank 段展开（本机实测值按你站点的取值方式同理）
docker exec <CTN> printenv B12X_ROCE_PEER_HCA_MAPS | tr ';' '\n'
```

四个硬约束（不满足直接抛异常，**不会静默降级**）：

- 每个 rank 必须映射**全部非自身 rank 且各一次**（4 节点即 3 条），漏一个报
  `missing=[…]`；
- 同一 peer 的索引必须**互异**且落在 `[0, hca_count)` 内；
- HCA 数 > 2 且本表留空 → 直接 `RuntimeError`（"首靴留空、读 INFO 后填"这条
  模板注释在 4 口环网下是陷阱，留空必炸）；
- 改路径数必须同步改表，只改一边必炸。

**处置**：用本机实测值重写映射表，四机一致。别拿别人站点的表来"对齐"；仓内两
形态（环网/交换机）在这张表上互斥——环网形要逐秩表、交换机形删表走 flat 运行时，
两形键面不可混拼（`docs/RING-0.3.2-COMPAT.md` §1）。

## P1-4 ICMP / perftest 判不了对向通路

**现象**：对向 ping 不通；`ibv_rc_pingpong` / `ibv_write_bw` 对向一对连不上。
看着像"对向挂了"。

**根因**：对向通路靠硬件按 flow label 匹配转发（见 P1-1）。ICMP 与常规 perftest
都**不设 flow label**，所以对向一对**必然**连不上——这是预期，不是故障。perftest
的正确用法是测**邻居对**。

**判据**：对向连通性用真实起栈或 `in_hw` 规则计数（P1-1）来判，不用 ICMP/perftest。
若脚本里必须判 ping 结果，别写 `"0% packet loss" in out`——它会被
`"100% packet loss"` 命中，把全失败读成全通。要解析丢包数字本身：

```bash
out=$(ping -c 3 <H3> 2>&1); echo "$out" | awk -F',' '/packet loss/{print $0}'
# 读数字判断，不做子串匹配
```

**处置**：把"对向 ping 不通"从故障清单里删掉；把"perftest 对向失败"从故障清单
里删掉。别据此外报链路故障。

## P1-5 环内静态路由：必须挂在"该 path 真正用的那个口"上，挂错口 7 秒速败

**现象**：起栈 **7 秒速败**（是快速失败，不是慢）。

**根因**：内核 `ib_resolve_eth_dmac` 强制从 QP 自己的网卡做路由查找。静态路由
挂在别的口上、或下一跳不是该口的邻居，对向包就无路可走。手册里"路由表仅直连
4 条 fabric 子网 → 干净/不改"指的是**别加额外的全局路由**，**不是**"对向不要
路由"——这个误读会让人绕一大圈。

**判据**：逐条验收，必须命中"下一跳 = 该口邻居、出接口 = 该口"：

```bash
ip route get <对端IP> oif <IFACE>
# 期望输出形如：... via <邻居> dev <IFACE> ...
```

同一目标别挂在两个口上（二义性）。

**处置**：路由挂在那条 path 真正使用的口上，下一跳用该口的邻居。看到 7 秒速败，
先查路由挂口，再查别的。

## P1-6 GID 洞三件套：type + gid 值 + ndev，全零 `::` 才是洞

**现象**：起栈后才炸的 GID 类错误；读某口 RoCE GID 得到全零 `::`。

**根因**：通常是**该口没有 IPv4**（被 netplan apply / 重插线弄丢），RoCEv2 的
IPv4 GID 注册不出来。社区田野笔记还登记过同族症状：GID 从 index 3 漂到 index 4
（netplan/重插线后），判法是看 types/3 是否仍标 RoCE v2、v2@3 是否变空。

**判据**：读 GID 要**三件套**一起看（type、gid 值、ndev），只有 gid 值全零 `::`
才是洞：

```bash
cat /sys/class/infiniband/<hca>/port_1/gids/3
ibv_show_gid 2>/dev/null || echo "工具不可用，走 sysfs 三件套"
```

修完必须**四机复查**，一台好不代表四台好。

**处置**：把 IPv4 加回该口并四机复查；GID index 漂移的鉴别与恢复（重注册驱动）
见 `tools/packages/fabric-net/payload/runbook/COMMUNITY-FIELDNOTES.md` 症状 1。
别只修 head。

## P1-7 线材劣化判据是 Δ 速率，不是累计值；对调实验只在关机态做

**现象**：FEC corrected 计数高，怀疑线坏；或同一段线一头计数爆表。

**根因**：两个读数回答不同问题、互不背书——`rx_corrected_bits_phy` 是**当前速率**
（回答"现在哪一段在耗余量"）；守卫的翻转计数是**历史 down 次数**（回答"口在不在
反复掉"，受重启污染，见 P1-8）。一头爆可能只是自环（活环里 a↔b 互指，同段两端
都会报）。

**判据**：判据必须用 **Δ 速率**（两次采样相减，用 awk 算，别心算）；本底约
0–1/分，>100/分就要查：

```bash
ethtool -S <IFACE> | grep rx_corrected_bits_phy   # 相隔 60-120s 采两次相减
```

**处置**：判死线材用**对调实验**：两根线**整根换位、不换口、关机态**做——错误
跟着线走 = 线的锅。插拔/对调一律关机态（热插拔会降到 25000Mb/s，须重启恢复）。
`ethtool -m <IFACE>` 普通用户读不出模块 DOM，**读不到不等于没坏**，改用 FEC
速率判。另见社区症状 2：链路 state=ACTIVE 不作数（carrier 假活跃），要连续采样
`/sys/class/net/<IFACE>/carrier`（同上 COMMUNITY-FIELDNOTES 文档）。

## P1-8 重启会污染所有历史读数，先对轴再采信

**现象**：多台同时重启后，翻转计数与 FEC 历史读数全部飘红。

**根因**：一次整机重启就贡献十几条 up/down 抖动，全被算成"翻转"。这不是线在抖，
是计数被重启污染了。

**判据**：把事件按时间排出来，与 `uptime -s` / `last -x reboot` 对轴——事件全部
落在重启窗口内 = 计数噪声，不是线的问题：

```bash
uptime -s
last -x reboot | head
```

**处置**：重启后先重取基线，别拿重启前的告警当成现在的问题。任何翻转类告警，
判读前先对轴（守卫首巡高误报同根因，见 P6-2）。

# 二、启动面

env 注入、镜像/overlay/adapter 三层件、点火与停栈。这一层的共同特征是：
**大多数事故不报错**——它只是变慢、变旧、或者悄悄用了上一代的代码。

## P2-1 env 文件末尾缺换行，最后一行整个丢失（静默）

**现象**：env 里明明写了一行关键开关，进程里读不到，引擎回落源码默认值，**什么
错误都不报**。实测案例：丢了 `SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION=0`，
导致 `/health` 每次**真跑一发生成**、耗时稳定 1.00s——看着像健康检查慢，实际是
配置丢了。

**根因**：boot 脚本用 `while read` 逐行注入 env。文件末尾没有 `\n` 时，最后一行
不会被读出。丢的经常正好是关键开关——因为它在最后一行。

**判据**：

```bash
tail -c 1 <ENVFILE> | xxd                        # 末字节不是 0a 就是缺换行
docker exec <CTN> printenv | grep <末行键名>      # 空 = 已经丢了
```

**处置**：补上尾换行。注意三件事：①补换行会改变文件 md5，锚表里的形 md5 要同步
更新；②补换行**不改运行中的容器**，必须重靴才生效——报告时别写成"已生效"；
③该健康开关在环网形是仓内推荐键（`docs/RING-0.3.2-COMPAT.md` §2.3），丢了正属
于"回落默认值"这类静默坑。

## P2-2 overlay 影子目录会把新引擎盖回旧的

**现象**：镜像里明明是新引擎，启动直接
```
ImportError: cannot import name 'Selection' from <module>
```
或者更隐蔽——能起来，但跑的其实是上一代的代码。

**根因**：站点有一个**运行期挂载的覆盖层**（overlay 目录），挂载点在镜像内引擎
路径**之上**。镜像换对了，overlay 里的同名旧件照样把它盖回去。这条报错会把排查
引向 adapter/镜像，而真凶在 overlay。

**判据**（两侧 md5 必须同值）：

```bash
md5sum <PRODUCT_DIR>/overlay/<冲突文件名>
ssh <H1> 'docker exec <CTN> md5sum /<引擎源码路径>/<同名文件>'
```

**处置**：换引擎版本时**三步一起换**：①镜像；②adapter 全批（P2-3）；③overlay
里与引擎同名的件。换前整目录 `cp -p` 备份，四机都要换。通用律：`ImportError` /
`NameError` 指向某个只在某版本里存在的符号时，先去 overlay、adapter 这类"运行期
覆盖面"找同名件，**别只怀疑镜像**——镜像 md5 对了，不代表跑起来的是镜像那份。
overlay 面的挂载方式与计数断言见 `docs/DEPLOY-GUIDE.md` §5。

## P2-3 adapter 与引擎是绑定的，少换任一件就起不来

**现象**：只想升引擎、adapter 不动，启动就 `ImportError`；或者更糟——能起、能跑，
但长稳和位等静默出问题。典型形态：增量清单 13 件你换了 5 件，起不来，而报错只
指向 1 个模块名，看不出是"少换了一批"。

**根因**：新代 adapter 的核心件（分片、挂载缝、稀疏接线一类）依赖新代引擎才有的
符号与快速路径；反向也成立——旧 adapter 配新引擎，新引擎的快路径永远不被调用。
仓内绑定律正典见 `UPGRADE-0.3.2.md` §5（装载缝/分片/接线件必须与引擎同批）。

**判据**：装配后逐件对 manifest（注意过滤注释行，见 P3-7）；四机 adapter 面指纹
全等（指纹算法见 P2-11）。

装配核验（过滤注释行逐件对 manifest，期望输出 0）：

```bash
grep -E '^[0-9a-f]{32}  ' <MANIFEST> | (cd <PRODUCT_DIR>/adapter && md5sum -c -) | grep -vc ': OK$'
```

**处置**：引擎 + adapter **全批同批换、四个节点一起**；增量清单整批执行，**不要
凭感觉挑几件**；换引擎前先确认 adapter 整批件都拿到了，拿不到就整批不动。

## P2-4 读进程真参数看 `/proc/1/cmdline`，不是 `Config.Cmd`

**现象**：`docker inspect --format '{{json .Config.Cmd}}'` 里没有某个参数，你判
"参数没生效"。实际上容器是经 entrypoint / wrapper 脚本起栈的，`Config.Cmd` 只反映
镜像配置。也别信文档里的镜像标签——实测出现过文档说引擎是某版本、实跑是另一版本。

**根因**：两处含义不同——`Config.Cmd` 判**镜像设计意图**；`/proc/1/cmdline` 判
**实际跑的是什么**。

**判据**：

```bash
docker exec <CTN> sh -c 'tr "\0" " " < /proc/1/cmdline'
# 更强的运行时自省（能抓 argv 写了但没绑定的值）：
tools/serve_flags_gate.sh --api http://127.0.0.1:<PORT>
```

**处置**：两处都看。接线类旗标（`--tool-call-parser` / `--enable-cache-report` 等）
用 `tools/serve_flags_gate.sh` 从运行进程 argv 直证，判据表
见 `deploy/SPEC6-SERVE-REF.md`「旗标-能力-生效值对照表」，用法与退出码见
`tools/serve_flags_gate.README.md`。注意命名陷阱：`--tool-call-parser` 的值**连写**
（如 `deepseekv41`），`--reasoning-parser` 的值**带连字符**（如 `deepseek-v41`），
写反**不报错、功能静默缺失**；`/health` 200 不能证明接线成功。
另注意判据方向：`--sleep-on-idle` 自 2026-10-30 起为**禁参**（上游 sglang #43050
idle-wake hang host 侧规避）——argv **在场**才是红灯（缺席=正态），该判据已入
serve_flags_gate 缺席判据（R8）/env-lint EQ-03 禁参组合/selfcheck-prod 禁参表。

## P2-5 三层引号转发会把 `grep -A1` 打坏

**现象**：在 ssh → docker exec → sh 三层引号里 grep 参数值，只回一行旗标名、
没有值。

**根因**：三层引号转义会把 `grep -A1` 的行为打坏；而 `--xxx-size` 这类参数的值
在 cmdline 里位于**下一行**（NUL 转 `\n` 之后）。

**判据**：先落文件再 grep：

```bash
ssh <H1> 'docker exec <CTN> sh -c "tr \"\\0\" \"\\n\" < /proc/1/cmdline"' > /tmp/argv.txt
grep -A1 '^--chunked-prefill-size' /tmp/argv.txt    # 值在下一行
```

**处置**：任何多层引号下的管道 grep 都先落盘再查。别拿一条空输出当"参数不在"。

## P2-6 判负旗标常常成对出现，撤一个不撤另一个等于没撤

**现象**：按文档把 `--chunked-prefill-size` 改回 4096，但还带着
`--enable-mixed-chunk`，仍在违反另一条硬门。

**根因**：判负理由通常在三个地方各写一遍（SPEC 参考文档判负不进形 / CHANGELOG
组合窗裁定 / 运维手册禁键清单的"永禁 / 判负不进形 / 观察位"三级），配对关系写在
guard 配置里："回放旗标在场 ⇒ 混合批必须不在场"。仓内谱系：`deploy/SPEC6-SERVE-REF.md`
记 SPEC7（六参 + `--chunked-prefill-size 8192`）已判负不进形，正典值是 4096 且
没有 mixed-chunk 旗标。

**判据**：撤之前对禁键清单逐条 grep 已落盘的 argv（先按 P2-5 落盘）：

```bash
grep -E 'chunked-prefill-size|mixed-chunk' /tmp/argv.txt
```

**处置**：撤就**成对撤**。但两条纪律要说清：①**别据此宣称"引擎会拒起"**——实测
两旗标共存时引擎实际能正常起栈（硬门在 guard 侧台账，引擎源码里没有对应 raise），
定性只说"台账判负、与回放旗标互斥"，不要写"已触发故障"；②"当时跑着没坏"不等于
"合规"——测量说"这一格没退化"，规范说"这个值不许进形"，两者不冲突，**后者优先**，
别拿测量结论覆盖规范结论。

## P2-7 停栈脚本的自报不可信：两种假象 + 硬断言

**现象**：两种假象——①没有残留时打"head 无 / worker 无"（看着像成功，其实什么
都没停）；②**更危险**：有残留（旧的测试栈停着）时打 `[+] head removed` 四行全绿，
而产线容器纹丝不动（`Up 3 hours`）。

**根因**：最常见的是**脚本默认容器前缀与产线实际前缀不同**（脚本默认 `<PREFIX_A>`、
产线用 `<PREFIX_B>`），于是它"成功停掉"的是另一批容器。

**判据**：停栈后必须**硬断言**，不许信自报：

```bash
test "$(docker ps --format '{{.Names}}' | grep -c '<PREFIX>')" = "0" || exit 1
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<PORT>/health   # 期望 000（在 <H1> 上打，见 P5-1）
```

**处置**：任一不满足就 `exit` 中止，**绝不能进入沉降/点火**——否则沉降完会对着
一台还在跑的机器再点一次火，轻则抢锁失败，重则双引擎同机把统一内存挤爆。删容器
前先存旧栈日志（删了就没了）。

## P2-8 `BOOT_EXIT=2` / rc=2 不等于点火失败——先查是不是锁被抢了

**现象**：日志只有两三行（"靴槽锁被占" + pid/标签/start 三行），说明另一个点火器
先占了锁、你这一靴根本没跑。

**根因**：四机是单一靴槽（见 P9-7），锁是互斥不是排队。

**判据**（三步定性再下结论）：

```bash
docker ps | grep <PREFIX>                                  # 容器是不是已被别人点起来
docker inspect <CTN> --format '{{.State.StartedAt}}'       # 与锁里的 start= 时刻是否对齐
docker exec <CTN> sh -c 'tr "\0" "\n" < /proc/1/cmdline' | grep -A1 '^--'   # 跑的是不是你要的新配置
```

两个假信号别当真：`ps -p <pid>` 常返回"进程已退出"（点火器点完火就退了）；锁目录
也会空（锁已释放）。**别因锁已释放就当成没点过火。**

**处置**：三步定性后再下结论；是别人点的火就先协调处置，别急着把自己的改动回滚。

## P2-9 `@reboot` 开机自启与手动流程抢同一把锁

**现象**：手动点火窗口内偶发"锁被占"，且时间点与开机重合。

**根因**：head 机常配 `@reboot` 自启（开机后等 worker 可达即点火），与你的手动
流程竞态、顺序不确定。

**判据**：

```bash
crontab -l | grep reboot
```

**处置**：点火前先跑这条；想独占靴槽，先确认它不会在自己的点火窗口内触发。开机
链路上另一类竞态（网络规则脚本不等 IP 就绪）见 P6-8。

## P2-10 看注释判形会错——md5 一律实测

**现象**：启动脚本头注里写的 md5 与实际文件不符（写的是另一个文件的值），据此
判形出错。

**根因**：注释是手写的，会过期、会抄错；文件本体才是事实。

**判据**：

```bash
md5sum <BOOT> <ENVFILE>
```

锚值不用注释里的值，以仓内正档指纹表为准（如 `UPGRADE-0.3.2.md` §0 的目标形态
速查与 §6 的 env 键数/md5 口径——引用其原文，不在此抄录具体值）。

**处置**：判形一律实测哈希；注释只作线索、不作证据。

## P2-11 点火后四查与三个坑（漏跑等于白烧一靴）

**现象**：boot rc=0、端口 200，就认为验收通过——实际漏了"起没起对"的检查。

**根因**：四查是点火后的最低验收面：①`health` GET = 200；②`printenv` 四机真键
与 env 文件**逐字**一致；③横幅直读（在役态、各门状态可见）；④面指纹四机全等。
仓内正典口径见 `docs/DEPLOY-GUIDE.md` §7 与 `UPGRADE-0.3.2.md` §9（另含接线闸门
`tools/serve_flags_gate.sh` 与 warm 门 P9-2）。

**判据**：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<PORT>/health    # 200
docker exec <CTN> printenv | sort                                            # 与 <ENVFILE> 逐字比
tools/serve_flags_gate.sh --container <CTN-head> --container <CTN-worker>  # 退出 0
```

三个坑：①**横幅假报**——判读横幅要取组件源码里的 `print` 串，按手册里的名字 grep
可能得 0 行、误报"横幅缺失"，实际是大小写或缩写不同；②**启动耗时哨兵**——
`Engine startup timings` 的 `target_verify` 值 >75s = 红带靴预测（实测分离度
2/2：49s 绿 / 102s 红；健康带口径见 `docs/DEPLOY-GUIDE.md` §7），**红带现形即停靴
取证，不连发重试**；③**指纹要能复现**——指纹算法 = 对目标目录
`LC_ALL=C find -type f | sort -z | xargs -0 md5sum | md5sum`；如果某个历史指纹值
复现不出来（输入集没归档），**别再拿它做判据**，改用逐件对 manifest = 0 件差异
（更强、也可复现）。

**处置**：每次点火后固定跑四查 + 接线闸门 + warm 门；指纹的输入集要归档，否则
指纹只是"当时的数"。

# 三、换装面

升级不是"换个镜像"，是**四件东西同批换**：引擎镜像 + adapter 面 + overlay 影子件
+ boot/env 参数面。少换一件 = 能起能跑但静默回退。本章是"件从哪来、怎么算同源、
怎么判缺口"。

## P3-1 拓扑三档分拣：无关件能拿、绑定件只拿机制、专属件一件不拿

**现象**：从发布包或新代仓里拿了件来用——起不来（fail-closed）、或把别人的物理
接线值带进自己的站。

**根因**：新代发布件按"跟物理拓扑有没有关系"分三档，动作完全不同：

| 档 | 特征 | 动作 |
|---|---|---|
| 拓扑无关 | 纯计算/量具/参数面，环网与交换机通用 | 可以拿 |
| 拓扑绑定 | 编码了作者的物理布线、端口号、PFC/DSCP 规划 | 只拿机制不拿值；值一律本机实测 |
| 拓扑专属 | 只为某拓扑写的运行时与键 | 一件都不要拿，拿进来 fail-closed |

仓内正档就是这个分拣的实例：`docs/RING-0.3.2-COMPAT.md` §2 列环网可取的 0.3.2
件、§3 列仅属交换机形勿带到环网的件。

**判据**：对每件问一句"它跟物理拓扑有没有关系"；对照 `docs/RING-0.3.2-COMPAT.md`
§2/§3 的两张清单。拓扑绑定件三个典型：环图映射表（P1-3）、PFC/DSCP/traffic class
规划键、拓扑选择开关（flat / switched 这类）。

**处置**：无关件照拿；绑定件只拿机制不拿值；专属件明确列入"不要拿"清单**写进
任务书**（否则下一个接手的人一定会拿）。两形 env 不可整文件互抄——交换机形 env
含三个交换机键并删除了环网映射表，环网形要按键表手工增量（`UPGRADE-0.3.2.md`
§6 注记、`docs/RING-0.3.2-COMPAT.md` §2.3）。

## P3-2 digest 对不上 ≠ 不同源：逐层哈希 + 内容判据

**现象**：本站镜像 digest 与作者发布件不一致、层数也不一致，于是判"不同源、做不
到一致"。这条结论经常是错的，会导致"必须重新构建 / 买不到就得放弃"的错误决策。

**根因**：digest 是身份指纹，受基座层链与构建器影响；换基座/换构建器会得到不同
digest，即使内容一致。仓内正档明写豁免：此时"以源文件读回 md5 + 层数 + 单 COPY
层为内容判据，不要拿 digest 硬套"（`UPGRADE-0.3.2.md` §3.2）。

**判据**：比 `RootFS.Layers` 的**逐层 sha256**，不比总层数和 digest：

```bash
docker inspect --format '{{range .RootFS.Layers}}{{println .}}{{end}}' <IM_A> > /tmp/LA.txt
docker inspect --format '{{range .RootFS.Layers}}{{println .}}{{end}}' <IM_B> > /tmp/LB.txt
diff <(head -70 /tmp/LA.txt) <(head -70 /tmp/LB.txt)   # 空 = 同一基座（70 为示意基座层数）
docker run --rm --entrypoint /bin/sh <IM_NEW> -c 'cd <引擎源码目录> && git diff --stat'
# 上一条输出为空 = 零运行期源码改动
```

（注意 `docker inspect` 报的层数常比作者口径多 1，对表前先统一口径。）

**处置**：前若干层逐层相同 ⇒ **基座同源已证**，多出来的是自己烘的载荷层；再核
关键源文件 md5 逐件相等。报结论时**三层说清**：层哈希同不同 / 源文件 md5 同不同 /
差的是内容还是仅身份与层数——只说"digest 不同源"会把一个无功能影响的事报成缺口。

## P3-3 缺件取源第一顺位是镜像本体；四方权威顺序

**现象**：在交付仓里 grep 不到某个件，判"厂商没发"。实际上它烘在**镜像里**，或
在同作者的兄弟仓 / 上游依赖仓里。实测某发布包只有 3 个成员（镜像 tar + 说明 +
仓快照）——**交付包小不等于交付缺件**。

**根因**：镜像烘焙的载荷才是**随版本冻结的正典**；交付仓副本可能是脱敏改写版。
四方对账的权威顺序：**镜像烘焙件 > 基础设施仓（dev tip）> 脱敏交付仓副本 > 已装件**。

**判据**：导出镜像内烘焙件：

```bash
docker run --rm --entrypoint /bin/sh <IM> -c 'tar -C / -cf - opt/<kit>' > /tmp/baked.tar
```

判定两个件"是不是同代"用镜像身份里的 manifest 聚合 md5 复算（逐包
`cat MANIFEST.md5` 串联再 md5），相等即同代；**不要用文件名或时间戳猜**。

**处置**：报"锚值漂移 / 包账目 bug"之前，先对镜像烘焙件——拿脱敏交付仓副本去比
包内账目，会把"脱敏改写"误判成"包自己的账错了"（实测错报过一次）。先读交付仓
README 的"基础设施仓 / 上游 / 致谢"指引段再判"没发"。负结论写清已穷尽哪几处
（P8-4）。

## P3-4 问"仓库里有没有 X"必须按面回答，先问远端

**现象**：`ls` 了本地副本的某个目录就回答"没有"；实际它在另一个目录、另一条
分支、另一个 tag 里。一句"没有"会让人误以为要去找作者要包。

**根因**：一个版本通常分散在**多个面**——增量件（`deploy/reconstruct/<ver>/` 一类）、
env 形（可能仍是上一代，新代形只列在兼容档里）、兼容档（`docs/<VER>-COMPAT.md`，
拓扑能不能用的唯一权威）、tag 面（定版 / recon kit / baseline 三四个并存）。本地
克隆只是某时点的快照，不是仓库镜像。

**判据**：

```bash
git ls-remote --heads --tags <repo-url>   # 第一步永远是问远端（不吃 API 配额、不怕限流）
```

**处置**：按面回答："增量件在 A、env 形仍是旧代、拓扑形只有兼容档给的手工增量
路径、定版 tag 有三个"——这样才有用。

## P3-5 浅克隆的"落后 0"是假绿

**现象**：`git fetch` 报落后 0 提交，判"仓库没有更新"。

**根因**：浅克隆把历史截断了，fetch 读数不可信。

**判据**：

```bash
git rev-parse --is-shallow-repository   # true = 浅克隆，fetch 到 0 不可信
git rev-list --count HEAD               # 1 = 只有 1 个提交，历史被截断
```

**处置**：`git fetch --unshallow` 拉全历史，再看落后数。报"仓库没更新"之前必须
跑这两条。

## P3-6 `git status` 满屏改动可能全是权限位

**现象**：实测 1111 件 `mode 100644→100755`、0 增 0 删，看着像大面积改动。

**根因**：拷贝方式 / 挂载选项造成的权限位差异，不是内容改动。

**判据**：

```bash
git diff --summary | awk '{print $1}' | sort | uniq -c
```

**处置**：确认无实质改动后**别硬 pull**（易冲突），另拉干净 clone 做审计基准。

## P3-7 清单比对必须过滤注释行；判缺口三样都要过

**现象**：三类典型假缺口——①拿"清单行数 vs 文件数"判 adapter 缺件（差额其实来自
清单头部注释行被当成路径）；②只查某个挂载目录不存在就判 golden 表缺失（表其实在
仓库里，四机全在、逐字节相等）；③只比镜像总层数与 digest 就判不同源（P3-2 已驳）。

**根因**：比对口径错了。判缺口要**三样都过**：层哈希、逐件 md5、清单条数口径
（过滤注释行）。

**判据**：

```bash
grep -E '^[0-9a-f]{32}  ' <MANIFEST> | wc -l    # 只数真条目（32 位 md5 + 两个空格开头）
grep -E '^[0-9a-f]{32}  ' <MANIFEST> | (cd <目标目录> && md5sum -c -) | grep -vc ': OK$'
# 期望 0（无缺件/错件）
```

**处置**：作者文档明文豁免某项判据时（如"不要拿 digest 硬套"），**报缺口前先读
那句**。别把清单头部注释逐词当路径解析出假"缺件"。

# 四、通信面

升级里最贵的部分。核心认知：**通信档位是"绑定项"不是"可选调优"**；跨机失败的
日志天生不完全，归因要按行认机。

## P4-1 通信档位两键是绑定项，回滚即崩速

**现象**：高并发下**越并越慢的非单调塌陷**（c8 比 c4 还慢），单请求 tok/s 也一起
掉；加重预热不会好转。

**根因**：新代引擎的高并发路径依赖**更大的通信聚合窗口**（由两个键控制，本仓公开
键如聚合上限键族 `SGLANG_ROCE_MAX_SIZE` / `DSV41_ROCE_GATHER`）。回滚到旧档位 =
退回慢路径。A/B/A 实测（同镜像、同 adapter、同量具，只改这两键）：

| 并发 | A：新档位 | B：回滚旧档位 | A'：改回 |
|---|---|---|---|
| c1 | 正常 | −55% | 完全复原 |
| c4 | 正常 | −68% | 完全复原 |
| c8 | 正常 | −96% | 完全复原 |
| c16 | 正常 | −94% | 未测 |

**判据**：指纹 = **曲线随并发单调变差 + 单请求也掉**。这不是负载波动、也不是没
热透。环网形取这对键必须 A/B 验证（`docs/RING-0.3.2-COMPAT.md` §2.3 将其标为
"中风险；环网 4 口需 A/B"）。

**处置**：跑新代引擎就**不许回滚这两键**；任何"清理多余参数"的操作都不许动它，
否则性能掉一半以上且高并发塌陷。识别到指纹先查这两键有没有被改，别先去查网卡。

## P4-2 A/B 必须在新代引擎上做——旧代上做出来的结论会反

**现象**：同一对键，两拨人得出相反结论："无收益" vs "硬依赖"。这不是矛盾。

**根因**：旧代引擎没有依赖该窗口的 adapter 快路径，两档位差值落在噪声带内 ⇒
结论"这个键无收益"；新代引擎上回滚掉一半以上 ⇒ 结论"这个键是硬依赖"。
**改代之后，上一代的所有 A/B 结论全部失效。**

**判据**：判"某键要不要动"之前，先确认 A/B 是在哪一代引擎上做的；报告里写清
"这是哪一代引擎上的读数"，否则下一个人会拿旧结论覆盖你的。

代际取证（A/B 报告必须附带这两条的输出）：

```bash
docker inspect --format '{{.Config.Image}}' <CTN>
grep -E '^[0-9a-f]{32}  ' <MANIFEST> | (cd <PRODUCT_DIR>/adapter && md5sum -c -) | grep -vc ': OK$'   # 0 = 新代 adapter 整批在位
```

**处置**：换代后重做 A/B；旧结论不跨代引用。

## P4-3 失败点前移 = 上一处修复生效的证据

**现象**：修好 QP 建链后，死在更后面的**图捕获阶段**（报错见 P1-1 的
`vendor_err 0x81`），看着像"修了还坏"。

**根因**：链路问题修好后，流程推进到下一阶段才撞下一个坑。**失败点变了且更靠后，
本身就是前一处修复生效的证据。**

**判据**：N = 本机的**对向** rank，且**与路径数无关**——`OPPOSITE_PATHS` 设 2 或
4 报错逐字同形。

**处置**：别因为又失败了就把上一处改回去；先按 P1-1 查织网 `in_hw`。别去改
`OPPOSITE_PATHS`，白费一轮。

## P4-4 代理遇首错即中止，四台日志是不完全集

**现象**：四台日志各只留下**第一条**失败路径，据此推出"只有某条 rail / 某个口
坏了"——这是过度解读。

**根因**：代理遇首错即中止，后面的失败路径没有被执行，也就没有日志。

**判据**：要么抓齐四台日志再下结论，要么只陈述"首错在哪"。

四台各取首错（-m1 只取第一条失败路径）：

```bash
for h in <H1> <H2> <H3> <H4>; do echo "== $h"; ssh "$h" 'grep -m1 -n -i "failed" <日志文件>'; done
```

**处置**：别用不完全集做全量归因。

## P4-5 失败转储把四台日志拼在一起：按行认机，不按尾部

**现象**：转储尾部同时出现"写 rank 0"与"写 rank 1"两行，像一台机挂了两次。

**根因**：那是**两台 worker 各挂在自己的对向 rank 上**；拼接日志的行序不等于
单机时序。

**判据**：按每行所属容器 / rank 认机。

按行认机再归因（先标机、后统计）：

```bash
grep -nE 'rank [0-9]+' <失败转储文件> | head -20
```

**处置**：归因前先给每行标机，再数各机各自的失败。

# 五、读数面

怎么量才可信。这一层的通病是：**读数本身没错，取数方式错了**——缓存、冷态、
口径、下标，每一个都能把噪声读成结论。量具完整口径（PR filler 三档、DE mt400、
qeval、needle、每档 3 次取中位、引擎测试口与无鉴权约定）见 `tools/bench/README.md`。

## P5-1 引擎只绑回环，在别的机器上探活必 000（置顶第一条）

**现象**：在跳板机 / 管理机上 `curl 127.0.0.1:<PORT>` 得到 `000`，第一反应容易
是"引擎死了"。

**根因**：引擎刻意 `--host 127.0.0.1`（不扩大暴露面，这是设计不是缺陷）。别的
机器上的 `127.0.0.1` 不是引擎。

**判据**：一切探活 / 契约测试必须 ssh 到 head 机上打回环：

```bash
ssh <H1> 'curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:<PORT>/health'   # 期望 200
```

**处置**：000 的第一反应是"我打错机器了"，不是"引擎死了"。停栈断言里期望 000
（P2-7）同理必须在 head 上打。重启后 API 000 还有一种可能是自启单元为空（P6-7），
先分清这两种。

## P5-2 radix 前缀缓存吃掉你的重复请求（假绿）

**现象**：同一批探测连跑三次，第二次起耗时从 84.8s 掉到 1.9s，像"提速 45 倍"；
或手发同一 58k 提示，第 2 次起 0.33s / 167k tok/s。

**根因**：引擎整段命中 radix 前缀缓存，只补新增 token；耗时差异来自缓存，不是
性能变化。量具自带 nonce 时不受影响，**手发 curl 必须自己把独立 nonce 放提示词
开头**，否则后几次全被前缀缓存吃掉。

**判据**：查 `prompt_tokens`——与前一次**完全相同** ⇒ 差异来自缓存：

```bash
python3 -c "import json;d=json.load(open('<FILE>'));print([r['prompt_tokens'] for r in d['pr']])"
```

**处置**：要把耗时当性能指标，每轮必须换 nonce / 新提示词。量具读数与手发读数
不可互比。

## P5-3 冷态税落在批次第一格，能低到近一半；塌陷点每轮换位

**现象**：实测同靴 PR 8k 档三轮 5397/5369/**2378**、32k 档三轮 **4352**/6188/6202
——两条最低读数都是批次里先跑的那一发；PR 首档 2492（−52%）、DE 首格 50.9
（−41.9%），空载后单独复测 3 发中位 90.6（比基线**高** 3.3%）。

**根因**：冷态税（缓存 / 页表 / 图未热）。多档批次里塌陷点**每轮换地方**（第 1 轮
16k 塌、第 3 轮 8k 与 32k 塌，同档其余两轮都在正常带内）——单看任意一轮都会报出
"−45% 回归"；按档取三轮中位后全部落回 ±5%。

**判据**："某一格暴跌**且是批次里最先跑的那格**" ⇒ **先复测，别直接报回归**；
曲线**单调性**（后续档位能不能爬回来）才是干净信号。

同档三次独立调用取中位（示例为 PR 档；DE 同理）：

```bash
for i in 1 2 3; do
  python3 <repo>/tools/bench/sd_bench.py --mode pr --sizes 8192 --pr-filler real \
    --base-url http://127.0.0.1:<PORT>/v1 --key-file /dev/null --json-out /tmp/rerun_${i}.json
done
```

**处置**：每档至少 3 次独立调用取中位。"64k×3" = **跑 3 次独立调用取中位**，不是
`--runs 3`（该参数在 PR 模式可能被忽略，见 P5-12 与 `tools/bench/README.md` §1）。

## P5-4 并发曲线的非单调凹陷点要复现两次才认

**现象**：c1→c2→**c4（凹陷）**→c8→c16。

**根因**：单次出现的非单调点一律归为噪声；只有两组独立测试都复现的，才是真实的
batching 边界现象。

**判据**：两组独立测试都复现该凹陷。

两轮独立的全档扫描，比对两轮是否都在同一档凹陷：

```bash
for r in 1 2; do for c in 1 2 4 8 16; do
  python3 <repo>/tools/bench/sd_bench.py --mode de --type structured --concurrency "$c" \
    --base-url http://127.0.0.1:<PORT>/v1 --key-file /dev/null --json-out /tmp/de_r${r}_c${c}.json
done; done
```

**处置**：写进报告要注明"现象已复现、根因未查"；单次凹陷不报。

## P5-5 `agg` 是 ragged 负载指标：先看 `completion` 数组再比读数

**现象**：Structured 档同并发读数天然带 25%~65% 极差（同批 16 路会生成 30~400
各种长度），像性能大幅波动。

**根因**：`agg = Σ(completion_i - 1) / (max(t_last) - min(t_first))`——分母由
批次里**最慢那条**决定，分子是**实际产出量**。各请求生成长度不一样，读数自己漂。
Structured 是负载最不齐的一档（模型自己决定停在哪）。

**判据**：报数前把 `de[].completion` 打出来看一眼；各轮形状不一致，就不许把差异
读成提速/回归：

```bash
python3 -c "import json;d=json.load(open('<FILE>'));print([e['completion'] for e in d['de']])"
```

**处置**：对齐负载形状或改用稳定口径；DE 数字只与 mt400 正典口径比，不要拿 mt64
或仪表盘数字对照（`tools/bench/README.md` §3）。

## P5-6 取 `de[0]` 当结论是错的，要取中位

**现象**：三轮 85.88/88.64/89.59，取 `de[0]`=85.88（首轮冷态值）报"提升 69%"是
错的（中位 88.64）。

**根因**：单格 json 里存的是**多轮 `de[]` 数组**，不是单值；`[0]` 恰好是冷态首轮。

**判据**：

```bash
python3 -c "import json,statistics;d=json.load(open('<FILE>'));print(statistics.median([e['per'] for e in d['de']]))"
```

**处置**：跨批次对比**两边都必须取中位**。读数与历史基线不符时，第一动作是查
取数方式（P8-10）。

## P5-7 单流 tok/s 取决于内容类型，不是唯一值

**现象**：同引擎、同并发、同 `max_tokens`，实测：Prose 88.8 / Code 141.4 /
Structured 160.9（tok/s，示意量级）。

**根因**：投机解码的 draft 接受率依赖内容的可预测性——散文最不可预测、结构化
字段最可预测。

**判据**：报"这台机器多少 tok/s"必须带内容类型。

同一引擎三种内容类型各跑一发，确认读数分层：

```bash
for t in prose code structured; do
  python3 <repo>/tools/bench/sd_bench.py --mode de --type "$t" --concurrency 1 \
    --base-url http://127.0.0.1:<PORT>/v1 --key-file /dev/null --json-out /tmp/type_${t}.json
done
```

**处置**：跨类型横比是误用；对表前先对齐内容类型与口径。

## P5-8 填充口径影响读数：`repeated` 比 `real` 虚增约 10%

**现象**：同靴同尺寸 64k：`repeated` 6056 vs `real` 5507。

**根因**：`repeated` 重复同一短语，行缓存放大重复单元命中率。

**判据**：跨环境比对前先对齐 filler 口径；历史读数若是 repeated 口径，不可与 real
读数直接比。

同靴同尺寸两种 filler 对照（期望差约 10% 量级）：

```bash
for f in repeated real; do
  python3 <repo>/tools/bench/sd_bench.py --mode pr --sizes 65536 --pr-filler "$f" \
    --base-url http://127.0.0.1:<PORT>/v1 --key-file /dev/null --json-out /tmp/pr_${f}.json
done
```

**处置**：锚值 / 门读数一律用真实文本填充。三档口径（repeated / random / real）
的定义与用途见 `tools/bench/README.md` §2。

## P5-9 并发干扰的签名是"首轮暴跌、即刻恢复"

**现象**：独占组 5 轮 164.4~164.9（中位 164.5）；同时打大请求的干扰组
**74.5/147.8**/162.8/163.1/164.2（中位 163.1）——只砸前 1–2 轮，随后满速。

**根因**：并发的大请求抢占了引擎；批内很快稳定，5 轮取中位后几乎看不出。

**判据**：**整批每轮都均匀低 ⇒ 不是并发干扰**，别往"有人在抢引擎"方向查。

打印逐轮单流值看签名（前 1-2 轮低 = 干扰；均匀低 = 不是干扰）：

```bash
python3 -c "import json;d=json.load(open('<FILE>'));print([e['per'] for e in d['de']])"
```

**处置**：跑吞吐前确认引擎独占（质量跑分与吞吐跑分绝不并发，P5-15）；受污染档
空载后复测。

## P5-10 长量具必须 nohup 落文件，轮询产物目录收尾

**现象**：PR 七档 × 3 全程 >7 分钟，前台 ssh 会话被超时掐断；脚本里没 nohup 时
**ssh 断 = 任务死**。

**根因**：前台会话的生命期绑在 ssh 连接上；且 ssh 被杀后脚本可能**仍在远端继续
跑**。

**判据**：

```bash
ssh <H1> 'nohup bash /tmp/<script>.sh > /tmp/<script>.log 2>&1 &'
# 收尾：先确认进程死活，再数产物
ssh <H1> 'pgrep -af <script>; ls <产物目录> | wc -l'
```

**处置**：轮询**产物目录文件数**收尾，别轮询日志内容；先 `pgrep -af` 确认进程
死活再决定下一步，**不要盲目重发**（会双跑互扰）。

## P5-11 `rsync` 可能不存在，用 tar 管道替代

**现象**：判完成后拉结果文件，远端报 `rsync: command not found`，收尾卡住。

**根因**：精简 OS 镜像 / 最小安装的目标机常不带 rsync；ssh 管道 + tar 是处处可用的替代。

**判据**：

```bash
ssh <H1> 'cd <目录> && tar czf - *.json' | tar xzf - -C <本地目录>
```

**处置**：远端路径里的 `~` 在部分嵌套引号下不展开，写 `$HOME` 或绝对路径更稳。

## P5-12 量具参数各不相同：大片 405/404 先查拼接口径

**现象**：大量 405 / 404，像引擎坏了。

**根因**：各量具拼 URL 的约定不同：

| 量具 | 正确参数 | 典型错法 |
|---|---|---|
| qeval | 子命令式 `run <label> --url <全路径>/v1/chat/completions` | 只给根路径 → 405 |
| sd_bench | `--base-url .../v1`（脚本自拼 `/chat/completions`） | 给到 `/v1/chat/completions` → 405 |
| gsm8k | `--base`（**不带 `/v1`**）、`--out-summary`、`--out-raw` | 用 `--base-url` 不被识别；带 `/v1` → 拼成 `/v1/v1/` 全 404 |
| needle | `--base` **不带 `/v1`**；600k 档必须显式指定形态 | 用 auto 会退到低档红线 |

**判据**：看到大量 404 先看是不是 `/v1` 被拼了两遍，不要先去查引擎。

**处置**：`--concurrency 1 2 4 8 16` 这种空格多值不被接受，**逐档串行循环**跑。
PR 档位参数名是 `--sizes` 不是 `--targets`：写错时 argparse 直接拒起，**管道里
grep 后变成静默空输出**（看着像量具坏了）。量具命令一律先跑一次 `--help` 或确认
json 落了地，**别拿空输出当"跑过了"**。统一约定（测试口、无鉴权 `--key-file
/dev/null`、每档 3 次取中位）见 `tools/bench/README.md` §1。

## P5-13 读 JSON 前先打一次字段名

**现象**：凭猜读字段，白读一轮空值。

**根因**：两个量具的字段名不一样——PR 顶层 `{label, pr:[…]}`，每行
`{target, prompt_tokens, ttft_s, tok_s, …}`；DE 顶层 `{label, de:[…]}`，每行
`{type, conc, per, per_all, agg, completion}`（**没有** `agg_tok_s`/`tok_s`；单流
看 `per`，聚合看 `agg`）。

**判据**：

```bash
python3 -c "import json;d=json.load(open('<FILE>'));print(list(d));print(json.dumps((d.get('pr') or d.get('de'))[0]))"
```

**处置**：先探形再取数。

## P5-14 验长上下文用"检索题"，不要用"计数题"

**现象**：给 12k 提示 + `max_tokens=4000`，返回 `finish=length` 且 `content` 是
**空串**，看着像链路坏了。

**根因**：那道题要数数，思考链把 4000 token 全吃光（`completion_tokens=4000` =
撞到上限）——是**预算问题，不是链路问题**。

**判据**：看 `usage.completion_tokens` 是否撞到 `max_tokens` 上限；撞了就是预算
问题。

**处置**：换成**不需要长推理**的提取题（"只回答标记后四位"），实测 `finish=stop`、
精准答对、思考仅 107 字符。needle 量具的长上下文口径见 `tools/bench/README.md` §6。

## P5-15 质量跑分与吞吐跑分绝不同时上引擎

**现象**：GSM8K 一类质量跑分与吞吐跑分并发，各档读数被拉低三到四成，事后无法
区分"真实差距"与"干扰"。

**根因**：两者互相抢卡。

**判据**：排好队串行跑。

开跑前确认引擎上没有别的量具在跑（期望 CLEAN）：

```bash
ssh <H1> 'pgrep -af "sd_bench|gsm8k|qeval|needle" || echo CLEAN'
```

**处置**：受污染的档在引擎空闲后**干净复测再采信**。跨形态（环网 vs 交换机）
读数同样不可互比——每个形态先建自己的同形基线（`tools/bench/README.md` 跨形态
纪律、`docs/RING-0.3.2-COMPAT.md` §5）。

## P5-16 统一内存架构下，常规工具读不到 GPU 侧占用

**现象**：`nvidia-smi memory.used` / `ps` RSS / 容器 cgroup 全显示 `N/A` 或不可用
——显示 `N/A` 不是故障。

**根因**：GB10 统一内存（UMA）架构下这些工具的统计面不覆盖。

**判据**：唯一可靠量法 = `/proc/meminfo` 穷举分类取残差。

**处置**：**禁止用"内存比例参数 × 总内存 − 各项估算"倒推"剩多少给 OS"**——那个
比例是"在**可用内存**里拿 N% 建静态区"，不是"占总内存 N%"，据此倒推会凭空造出
不存在的数。报不出的量就不给数字，先实测。

## P5-17 `MemAvailable` 只能从 `/proc/meminfo` 取，别用 `free` 第 4 列

**现象**：`free` 第 4 列只剩 1–3 GiB，看着像要 OOM；实际机器很健康（实测误报过）。

**根因**：`free` 第 4 列是**纯空闲**，引擎起来后会被页缓存吃剩很少；真实可用在
`MemAvailable`。

**判据**：

```bash
awk '/^MemAvailable:/{print $2/1024" MiB"}' /proc/meminfo
```

**处置**：水位类判断一律取 `MemAvailable`；needle 长上下文形的水位门校准也以实测
为准（`tools/bench/README.md` §6）。

## P5-18 功耗低 ≠ 降频，降频判定只有一条路

**现象**：`96% util / 28~31W / SM 2379 MHz（上限 3003）`，看着像被限功耗——实测
不是。

**根因**：功耗计数器非零只说明**历史上**碰过功率墙；它跟当前是否降频是两回事。

**判据**（唯一判法）：

```bash
nvidia-smi -q -d PERFORMANCE
# 期望：Performance State: P0
#       Clocks Event Reasons: SW Power Cap / HW Slowdown / ... 全部 Not Active
```

**处置**：整机 UMA 形报 `Current/Max Power Limit` 为 `N/A` 是正常的，别拿它判
"限功率被设错"；**别用功耗数字反推降频**，白查一轮。

# 六、守卫与服务面

guard 守卫、网关代理、systemd 单元。这一层的坑大多是**静默的**：守卫不告警、
代理指向错、单元是空的——都不报错。

## P6-1 上游守卫脚本的两处静默失效 bug（照抄上游安装必中）

**现象**：守卫装上了、也在跑，但真实过载时**永不告警**——不报错、只是盲。

**根因**：上游脚本两处 bug，都是静默的：

1. **idle 门不认 loads 包裹**——作者只认顶层 list 与 `num_queue_reqs`；实际引擎
   返回 `{"loads":[{num_running_reqs,num_waiting_reqs,…}]}`，于是真实在飞请求时
   仍读到 (0,0)，盲判空闲；
2. **浮点比较恒假**——`[ "$v" -gt "$hi" ]` 拿整数测试比浮点（如 2249.6），报
   "需要整数表达式"、verdict 恒 0，永不告警。

**判据**（自证两条）：

```bash
curl -s http://127.0.0.1:<PORT>/v1/loads | head -c 200
# 期望看到 {"loads":[…]} 包裹形
curl -s http://127.0.0.1:<PORT>/v1/loads | python3 -c \
  'import json,sys;d=json.load(sys.stdin);print(d["loads"][0]["num_running_reqs"], d["loads"][0]["num_waiting_reqs"])'
grep -rn "get('loads'\|\['loads'\]" <守卫安装目录>/guards/    # 零命中 = 上游没处理这层
```

**处置**（修法各一句）：①idle 门改为从 `loads[0]` 取 `num_running_reqs` /
`num_waiting_reqs`（兼容旧顶层形）；②带外判据改用浮点比较，如
`awk -v a="$v" -v b="$hi" 'BEGIN{exit !(a>b)}'`。一律用站点适配形，**并把修复
推回上游**——否则下次谁照上游重装谁中招，且完全静默。

## P6-2 守卫第一次巡检会红很多，大部分不是真故障

**现象**：初装首巡一片红。

**根因**（分项）：

- **prio0 收缓冲 / PFC prio3、5**：常是前置硬化遗留（旧信任模式），新信任模式下
  这些队列空闲，未配不影响环网——不是故障；
- **FEC corrected 阈值**：**这项要当真**。用 Δ 速率逐口看绝对量（P1-7），差
  5 个数量级 = 线材/接口物理问题；
- **物理层翻转计数 = 高误报项**：一次整机重启贡献十几条抖动，先对重启时间轴
  （P1-8）再采信；
- **注册面 drift 连续 3 轮升级为 CRIT-STANDING**：修好后需 **6 轮绿**才滞回清除，
  不是修好立刻清；
- **恢复门硬编码主机名**：站点主机名不同则永远 no-op（装齐即可）；
- **哨兵 / 基准脚本**是作者车队绑定件（内网 registry、作者机地址一类）——跑
  起来必须先做站点适配，别以为装上就能用。

**判据**：按上列分项逐条判，别把整片红当整片故障。

按分项过滤守卫巡检输出，逐条归类后再判：

```bash
journalctl -u <守卫单元> --since today | grep -Ei 'pfc|fec|flap|drift|recover' | head -30
```

**处置**：FEC 当真；其余先核实适用性；CRIT-STANDING 等 6 轮绿。

## P6-3 守卫件的三个站点适配点（不做就跑不顺）

**现象**：守卫装好后自检 FAIL / 路由双双假红 / 诊断脚本三字段 JSON 出口失能。

**根因**：①topology 的 `hosts` 键必须是**真主机名**（自检工具用
`socket.gethostname()` 取键，填别名必 FAIL）；②路由字段要按 `ip route` 的**打印
形**写——主机路由不带 `/32`（P7-1），写成 `/32` 会在字符串匹配时双双假红；
③诊断脚本的公共库路径（`PKG_LIB` 一类）可能解析到不存在的层级。

**判据**：逐点跑守卫自检（`--selftest` 类入口）期望全过；路由字段与本机
`ip route` 输出逐字比对。

**处置**：hosts 填真主机名；路由字段照 `ip route` 原文；把库文件放到脚本实际
查找的那一级。

## P6-4 网关代理不在点火链里：引擎健康、主链全挂

**现象**：引擎 health 200，但经网关的主链全挂。

**根因**：并发代理是**独立容器/服务**，不在点火脚本、槽锁、启动链里。引擎重启
后代理可能还指着旧地址，或自身已挂。

**判据**（一条命令看清主链底部指向）：

```bash
docker exec <网关容器> sh -c 'grep -n UPSTREAM_BASE /app/config.yaml; env | grep -i upstream'
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<GW_PORT>/health
```

诊断顺序：先 `curl` 代理口 health，再打主链入口 `/v1/models`。

**处置**：排障从主链底部指向往上查；别只看引擎 health 就下"引擎坏了"的结论。

## P6-5 模型清单以网关的 `/v1/models` 为准，主链入口那份是静态别名表

**现象**：主链入口（LiteLLM 类）的 `/v1/models` **同时列出引擎上已不存在的旧
模型名**，且旧名打进去照样返回结果。

**根因**：那是一张**静态别名表**；引擎不校验请求里的 model 字段。旧名可用 ≠
旧模型还在跑。

**判据**：判断引擎在跑哪个模型，从引擎/网关侧取真实清单，别拿主链入口的列表。

引擎侧与主链入口的模型清单比对（在 <H1> 上执行；差集 = 静态别名）：

```bash
diff <(curl -s http://127.0.0.1:<PORT>/v1/models | python3 -c 'import json,sys;print(*sorted(m["id"] for m in json.load(sys.stdin)["data"]),sep="\n")') \
     <(curl -s http://127.0.0.1:<GW_PORT>/v1/models | python3 -c 'import json,sys;print(*sorted(m["id"] for m in json.load(sys.stdin)["data"]),sep="\n")')
```

**处置**：换模型后旧名仍返回结果时，别误判"没切过去"。另注：客户端模型发现面
还有一类 `/v1/models` 容量键缺失坑（缺 context_length 等四键会落默认窗、把成功
响应误判超限），与本题不同源，见 `docs/DEPLOY-GUIDE.md` §9.4。

## P6-6 `INJECT_ENABLE_THINKING` 在旧版网关是假键

**现象**：照模板补 `INJECT_ENABLE_THINKING=1`，升级网关后**行为反转**。

**根因**：旧版网关注入的 `enable_thinking` 对某些模型**无效**，真正的键是
`chat_template_kwargs.thinking`。

**判据**：对照你的网关版本与注入键清单（网关载荷 README / config），确认注入的
是哪一个键。

核网关实际注入的 thinking 键：

```bash
docker exec <网关容器> sh -c 'grep -rn "thinking" /app/ 2>/dev/null | head; printenv | grep -i think'
```

**处置**：修好真键之前**保持 0 反而安全**；升级网关前先核注入面，别照模板直接
补键。

## P6-7 启动链的最弱环：mesh 无重试、marker 无守卫、引擎自启单元常空

**现象**：整机重启后出现——对向 2 跳静默失效（守卫只记 WARN 不修）；marker 无
任何守卫覆盖；`After=network-online.target` 对"地址就绪"零保证；**引擎自启单元
常为空** → 重启后 API 是 000，须人工拉。

**根因**：启动链各单元的守卫覆盖不均，最弱环决定整体可靠性。

**判据**：重启后逐项核：织网 `in_hw` 计数（P1-1）、引擎口 health（P5-1）、
`systemctl list-units | grep -Ei 'mesh|fabric'`、引擎自启单元状态。

**处置**：把"重启后人工拉一把"写进运维手册（这是当前设计的预期动作）；要把
根治做进去（等 IP 就绪的覆盖单元 / 重启策略）**必须先请示**，别自作主张改第三方
启动链。

## P6-8 开机竞态是已知隐患：先量化罕见度再说话

**现象**：偶发 mesh 单元失败、路由报错，`set -euo pipefail` 使服务退出码非 0 判
失败。

**根因**：第三方脚本时序——驱动预置（`devlink driver_reinit` 每口停约 4s）+
信任模式切换再抖一次之后，**网络规则脚本没有等 IP 恢复就加路由**，而它的第一道
检查只等 `operstate=up`（**物理链路 ≠ IP 就绪**）。四台脚本一样，只是时序赌赢
赌输。

**判据**（量它多罕见）：

```bash
journalctl -u <单元> | grep -c 'mesh-up OK'    # 成功次数
journalctl -u <单元> | grep -c Nexthop         # 竞态失败次数（实测全环 46 成 / 1 败量级）
```

**处置**：处理就是**事后手动拉一把**（显示 `activating` 是在逐口调参数、约 7s/口，
等即可，不是故障）。别把它当硬件或显存改动引起的；别自作主张根治（同 P6-7）。

## P6-9 前置守卫拦"GPU 被占"，先看 PID 活不活

**现象**：起栈被前置守卫（`--query-compute-apps=pid` 一类）拦下，看似有人在用卡。

**根因**：那一栏可能是**瞬时**占用——已消失的进程、图形栈残留。

**判据**：

```bash
nvidia-smi --query-compute-apps=pid --format=csv,noheader | while read p; do
  [ -d "/proc/$p" ] || echo "$p 已退出（瞬时占用）"
done
nvidia-smi   # 再看 Processes 面板：背景进程占十几 MiB 不阻碍起栈
```

**处置**：逐 PID 核活再下结论。别把一次瞬时占用当成"有人在用卡"而白白放弃一靴。

# 七、复核面

复核命令自身的坑。**假阴性比假阳性更阴险**：读错字段、读错命名空间、工具静默
给空——都不报错，你会拿着假读数下真结论。

## P7-1 `ip route show` 对主机路由不打印 `/32`

**现象**：`ip route show | grep '/32'` 为空，判"路由丢了"。

**根因**：主机路由打印时**不带** `/32` 前缀。

**判据**：改用 `ip route get <对端IP>` 直接验证命中（期望 `via <邻居> dev <IFACE>`，
同 P1-5）。

**处置**：grep 路由用网段前缀或改用 `ip route get`；守卫的路由字段也要按打印形写
（P6-3）。

## P7-2 容器内复核漏 `nsenter` = 假 0

**现象**：inline ssh 进容器直接跑 `tc` / `systemctl` / `devlink`，读到 0 或空，
判"没配置"。

**根因**：读的是**容器自身命名空间**，不是宿主的。

**判据**：

```bash
docker exec <CTN> nsenter -t 1 -m -u -i -n -p -- tc filter show dev <IFACE> ingress
```

**处置**：凡进容器复核宿主面（网络栈/systemd/驱动），必带
`nsenter -t 1 -m -u -i -n -p`。

## P7-3 `ethtool -G` 打两段、PFC 按位序：读错段 = 假读数

**现象**：把"pre-set maximum（最大档）"当"当前档"读；PFC 计数读错段。

**根因**：`ethtool -G <IFACE> rx` 输出**两段**（最大档与当前值）；PFC 行是**按
位序**排列，不是数逗号段。读错字段比读不到更危险——**它不报错**。

**判据**：先断言一个已知真值（P7-6）再采信其余读数；逐段核对字段名。

ethtool -G 全文并打——认准两段标题，当前档取第二段 Current hardware settings：

```bash
ethtool -G <IFACE>
```

**处置**：探针脚本对每个解析字段写明取哪一段；两段并打人工核对一次。

## P7-4 `ethtool -i` 在普通用户下静默给空

**现象**：`ethtool -i <IFACE>` 无输出、无报错。

**根因**：需要 root；普通用户下**静默空**（不报错也不提示）。

**判据**（查网卡固件/驱动走 sysfs + modinfo 替代）：

```bash
modinfo mlx5_core | head -5
cat /sys/class/net/<IFACE>/device/vendor /sys/class/net/<IFACE>/device/device 2>/dev/null
```

**处置**：别把空输出当"没有驱动信息"；需要 ethtool 全功能时用 root 执行。

## P7-5 校验脚本必须在被测机上跑，且内层不套 docker

**现象**：内含 `docker run` / `nsenter` 的核查脚本在管理机上跑，打到**管理机自己
的 docker**（容器名不存在 → 假失败）；或在容器里再套 docker 直接挂。

**根因**：脚本默认作用于本机 docker 守护进程；嵌套 docker 在容器内不可用。

**判据**：一律 ssh 到目标机执行；内层脚本只写宿主命令、不再套 docker。

脚本头部目标机断言（防在管理机上误跑）：

```bash
test "$(hostname)" = "<目标主机名>" || { echo "跑错机器，中止"; exit 1; }
```

**处置**：脚本头部加目标机断言（hostname 核对不符即退出），防跑错机。

## P7-6 凡探针，先断言一个已知真值

**现象**：探针脚本输出一串读数，某些字段解析错了也不报错——假读数直接进结论。

**根因**：解析错段 / 错字段 / 错单位都是静默的。

**判据**：探针第一个动作对一个**已知真值**做断言（如某口必然有 IP、某单元必然
active、某文件必然存在），断言失败即退出不输出。

正控制断言示例（放在探针取数之前）：

```bash
[ -n "$(ip -4 addr show <IFACE> 2>/dev/null | grep inet)" ] || { echo "正控制失败：<IFACE> 应有 IPv4"; exit 1; }
```

**处置**：把正控制写进探针；无断言的读数不采信。这条是 P7-3 的通用化。

# 八、判断面

怎么定性才不错报。这一面的共同点：**命令都对、读数都对，错的是结论的级别**——
把线索当结论、把一代的规范套另一代、把噪声读成回归。

## P8-1 形面对表只是上半场，必须按实际使用方式打真请求

**现象**（整册最重要的一条）：一轮审计里 51 键 env 逐字对上、启动参数齐、横幅
正常、面指纹四机全等、NCCL 版本对上 ⇒ 结论"无 P0"；换"按实际使用方式打真请求"
一测，立刻暴出**工具调用解析器没配**、模型吐出的工具调用标记**漏成明文**给客户
端的 P0。

**根因**：形面检查证明"配置长对了"，不证明"功能合同是好的"。接线类旗标漏了，
`/health` 仍 200（静默降级，`deploy/SPEC6-SERVE-REF.md` 旗标-能力对照表）。

**判据**：验收必须两侧都做——**形面**（键面逐字 / 参数在位 / 横幅 / 面指纹四机
全等）+ **功能面**（带 `tools` 的 chat、流式、非流式、长上下文、经网关）。

**处置**：派审计任务时**必须写死两句话**：①只读，不碰容器/文件/进程，探活最多
一条小请求；②**必须按实际使用方式打真请求验证**（带 tools 的 chat、经网关、
流式/非流式），不只对照规范形。工具调用接线用 `tools/serve_flags_gate.sh` + 一条
带 tools 的真请求双证。

## P8-2 审计报告要逐条亲手复跑；定性只许四分类

**现象**：审计子代理擅长找线索、不擅长定性。实测三类误判：①把**已经配好**的
参数报成缺失 P0（只看了 `Config.Cmd`，没看 `/proc/1/cmdline`）；②把"站点按
**新版**兼容档照做"报成形面偏离（只读了**上一代**的档位表）；③拿**错的镜像/
文件**当证据。

**根因**：浅层命令 + 缺代际意识 + 缺证据链意识。

**判据**（验收三律）：

1. 凡 P0/P1，**自己用原文命令重跑一遍**，拿自己的输出才算数；不接受"它说"；
2. 每条结论要同时挂「**仓库路径 + 行号**」与「**本站命令 + 输出**」——只挂文档、
   没挂实测读数的，标为**未核实**；
3. 见到"应为 X、实为 Y"，先问：**X 是哪一代的规范？**再问：**这是哪个文件/
   哪个镜像里的 X？**（脱敏仓副本 ≠ 镜像烘焙件 ≠ 已装件）。

复跑模板（凡 P0/P1 逐条重跑并留档自己的输出）：

```bash
ssh <H1> '<原文命令>' | tee /tmp/recheck_$(date +%Y%m%d-%H%M%S).log
```

**处置**：定性只许**四分类**：真错 / 站点有意偏离（有书面依据）/ 站点强绑定值
（照抄即故障）/ 仓库值不适用于本站拓扑。**只有第一类进整改清单。**

## P8-3 有意偏离清单必须预声明进任务书

**现象**：不预声明时，映射表 / 回环绑定 / 通信档位两键 / 容器前缀 / 本地镜像这
五项，**每一个都会被当成 bug 报上来**，占掉复核大半时间。

**根因**：对比方不知道哪些差异是站点刻意为之。

**判据**：派对比任务前，把"有意偏离清单"写死进 context：哪个参数、本站值是什么、
为什么照抄会故障。

发任务书前自查五项偏离是否都已声明（期望五项各至少一行）：

```bash
grep -nE 'PEER_HCA_MAPS|回环|聚合上限|容器前缀|本地镜像' <任务书>
```

**处置**：不写这一条，对方会把"我们做对了"报成"我们偏了"。

## P8-4 报"缺件 / 没有方案"前走完六步 + 四件取证

**现象**：负结论（"这个仓库没有 X 的部署方案"）事后被推翻。

**根因**：搜索面不全。报负结论前按顺序走完六步：基座用途行 → 性能报告的形登记表
→ 模型注册卡 → 形态门 → 锚表行 → 才搜实件；并跑完"证不在"四件取证：git 全历史
（含已删分支）/ 脱敏映射语义 / 镜像内形清单 / 四机部署目录。

**判据**：每一步留下"查过、结果"记录。

取证命令示例（含已删历史的全量搜索 + 远端 tag 面）：

```bash
git log --all --oneline -- '*<关键词>*' | head
git ls-remote --heads --tags <repo-url> | grep -i <关键词>
```

**处置**：负结论要写"**已穷尽哪几处**"，不要只写"没找到"——否则别人无法复核，
也无法判断你漏了哪。仓内"有 / 没有"按面回答的口径见 P3-4。

## P8-5 两代文档并存：拿错代际会得出反向结论

**现象**：对着仓库文档逐项检查站点，检查出"站点偏离规范、应该改回去"，改完之后
**性能掉一半**。同一个键两代值不同（示意：通信聚合上限键族旧代 262144 / 新代
1179648 量级）。

**根因**：仓库常同时保留**旧代形档案**与**新代兼容档**，两张表同一个键、不同值。
旧代表不是"更保守的规范"，它是**上一代的规范**，同名键的值不可跨代套用。仓内
环网形/交换机形两档并存就是这个结构（`docs/RING-0.3.2-COMPAT.md`）。

**判据**：每对一次表，先确认两件事：这张文档是哪一代的、适用哪个形态。动手前
自问一句"我手上这张表是哪一代的？"

先给文档定代（最后改动时间轴 + 适用范围行）：

```bash
git log --follow --format='%ci %h %s' -- <文档路径> | head -5
grep -nE '适用|形态|ring|switch|0\.3\.[0-9]' <文档路径> | head
```

**处置**：以新代兼容档为唯一依据。"照做新代规范"的值**不是偏差，是照做了**——
别把它报成待修项。记错方向的代价最大：把做对的事当 bug 报上去，再在"照规范改
回来"的建议下砍掉一半以上性能。

## P8-6 宁可说"不可比"，不报站不住的差值

**现象**："我们比仓库快一倍"——查后发现是量具无 nonce（缓存虚增 16–42%）+
代际红利的叠加，那个数字一报就是错。

**根因**：三道前置没过就对表：①**代际不同**（新代有正向漂移红利）；②**量具
提示词没有 nonce**（反复打同一条 prompt，缓存虚增）；③**某些类型自己的误差棒
比差异宽**（仓库原文写明"小于自身波次离散度的逐行差异，本表分辨不了"）。

**判据**：三道缺一道就不能报差值。

nonce 自查（多轮 prompt_tokens 全同 = 缓存虚增，不可对表）：

```bash
python3 -c "import json;d=json.load(open('<FILE>'));ps=[r['prompt_tokens'] for r in d['pr']];print('NO-NONCE' if len(set(ps))==1 else 'OK')"
```

**处置**：能对表的只有三条：**类型排序、离散度结构、曲线单调性与峰位**。用户
记得住历史数字，用"正常浮动"糊过去会被当场问住，而且那个解释本身是假的——
**假解释会把下一次排查引向错误方向**。

## P8-7 自己加的每个键都是嫌疑犯（先查配置，后动硬件）

**现象**：引入厂商模板里没有的键后，冒出**只在你这份配置下存在**的门（自检类
代码常写"开了这个模式就只认 canonical 值"，而 canonical 只对作者那套接线成立）；
或按"改线对齐"先动了线，事后才发现根因是多设的一个键。

**根因**：新键会激活只对原作者环境成立的自检分支；物理改动掩盖了配置根因。

**判据**：出现"新门 / 新红"时，第一动作 = **撤掉自己加的键，回到生产口径**——
这是默认动作，成本是一个键。

列出自己在厂商模板之外加的键（输出即嫌疑犯清单）：

```bash
comm -13 <(grep -oE '^[A-Z0-9_]+=' <厂商模板env> | sort) <(grep -oE '^[A-Z0-9_]+=' <ENVFILE> | sort)
```

**处置**：只有确认该模式是硬需求时，才谈改硬件对齐——那是为满足这个模式付的
**物理代价，不可逆**。永远不要先让用户动硬件再回头查配置。

## P8-8 被要求"重跑一遍"时，不要原样重跑

**现象**：原样重跑 = 再摇一次骰子，同样的疑问大概率重现。

**根因**：产生疑问的是测量方式的弱点，不是被测对象变了。

**判据**：重跑前先改掉产生疑问的那个测量弱点——加 warmups、改取中位、跑前加热
身；但**只改测量参数，不改被测配置**。

复测带热身与多轮取中位（只改测量参数、不改被测配置）：

```bash
python3 <repo>/tools/bench/sd_bench.py --mode de --type prose --concurrency 4 \
  --runs 5 --warmups 2 --base-url http://127.0.0.1:<PORT>/v1 --key-file /dev/null \
  --json-out /tmp/retest.json
```

**处置**：保留上一轮产物作基线；报告里必须能区分"参数比基线好"与"配置相同"——
两者是不同的事实。

## P8-9 怀疑回归的正确复测形态：长窗口单格 8 轮

**现象**：单次读数低，分不清回归还是噪声。

**根因**：单次读数的噪声带可能比你怀疑的"回归"更宽；真回归会稳定复现。

**判据**：固定一格、确认空载、**一次调用跑 8 轮**看中位与极差——实测 8 轮
517/559/533/537/562/519/541/535 → 中位 536.1、极差 8.5% = 与基线同水平，才算
无回归；真回归实测形态是回滚即高并发档 −96%，**任何窗口都塌**。

长窗口单格 8 轮 + 中位/极差：

```bash
for i in $(seq 1 8); do
  python3 <repo>/tools/bench/sd_bench.py --mode de --type prose --concurrency 1 \
    --base-url http://127.0.0.1:<PORT>/v1 --key-file /dev/null --json-out /tmp/long_${i}.json
done
python3 -c "import json,statistics;vs=[e['per'] for i in range(1,9) for e in json.load(open('/tmp/long_%d.json'%i))['de']];print(vs);print('median',statistics.median(vs),'spread %.1f%%'%((max(vs)-min(vs))/statistics.median(vs)*100))"
```

**处置**：别把"形态不同"当成低值的现成解释——实测 `runs=1` 连打 8 个独立进程
读数 ±0.3（独立进程根本不受冷启动惩罚）；某批统一低 40% 的读数换形态后不复现 =
**时段性窗口变量，剃出基线**，不要为了解释它去编一个假机制。

## P8-10 读数与上次报出的数字不符，第一动作是查取数方式

**现象**：本轮单流 85.9 对上次报出的 89，第一反应答"落在长期带宽内，位置正常"
——结论错了。真实原因是本轮脚本逐格取 `de[0]`（首轮冷态）而历史基线取中位。

**根因**：取数口径变了，量没变。

**判据**：先复核三件事：**同一格、同一轮次口径、同一提取下标**；全部对齐后再
谈浮动。

把本轮与基线的取数口径同时打出来对齐（数组全打，不只打 [0]）：

```bash
python3 -c "import json;d=json.load(open('<FILE>'));print([e['per'] for e in d['de']])"
```

**处置**：宁可先查口径再谈浮动；假解释会把下一次排查引向错误方向（同 P8-6）。

# 九、运维面

停机窗、沉降、权重与配额、权限与死锁。这一面的纪律大多来自真实事故，违反的
代价按"事故"计。

## P9-1 沉降律：拆靴到点火 ≥600s 是硬约束，不是建议

**现象**：快速重启后首请求进 **940 级慢窗**——实测 warm 前 879 / 938 / 940，
warm 后 5972+，差一个数量级。

**根因**：前栈的资源面（缓存、内存、链路态）没有沉降完就点新火；"容器已净"
不等于"机器已静"。

**判据**：前栈拆靴 → 本靴点火之间静候 **≥600s**；多靴切换风险更高，必要时
≥30min。**禁以"容器已净"替代计时**——就是静候。仓内纪律同口径
（`UPGRADE-0.3.2.md` §2、`docs/DEPLOY-GUIDE.md` §7）。

**处置**：把 600s 写进停机窗 checklist；死锁整栈重启后的窗口同理
（`docs/deploy/DEADLOCK-MITIGATION-AND-FORENSICS-20261018.md`）。

## P9-2 warm 门规程：不跑热身就测吞吐，读数没有意义

**现象**：boot 完立即测吞吐，读数系统性偏低；首靴第一发偏低是常态（冷态税，
P5-3）。

**根因**：引擎各缓存面未热。

**判据**：boot rc=0 且端口 200 之后，**第一动作**是 warm 请求步 64k×2；然后
warm 门 64k×3 取**中位**：**≥4500 绿**（低于 4500 = 红，不起测），产线入役线
≥5000。仓内口径见 `docs/DEPLOY-GUIDE.md` §7 与 `UPGRADE-0.3.2.md` §9-§10.1。

**处置**："64k×3" = 3 次独立调用取中位，不是 `--runs 3`（该参数在 PR 模式可能被
忽略，P5-12）；锚值 / 门读数一律用真实文本填充（P5-8）。

## P9-3 换权重 ≠ 换 engram：二选一必做其一

**现象**：换权重后 boot 绿、契约过，但推理质量静默劣化。

**根因**：engram 是**从权重打包出的派生物**。换权重不换 engram = 新权重配旧权重
派生的 wkv 混跑；**引擎不会报错**（自检没跑 ≠ 自检通过）。

**判据**：判定新旧看文件 mtime 对权重下载/生成时间；分片身份对台账
（`UPGRADE-0.3.2.md` §4 的权重与 engram 台账）。

**处置**：换权重后必须**二选一**：从新权重重生成 engram，或跑质量锚对比旧读数、
定性混跑是否有害。权重走 NFS 位时，挂载健康要按 shard 数 `timeout` 逐点探——
软挂载假在线（挂载点死亡仍显 mounted），`mountpoint` 单查不可信
（`tools/packages/fabric-net/payload/runbook/COMMUNITY-FIELDNOTES.md` 症状 4）。

## P9-4 换模型 = 换形，不是换栈

**现象**：拿别的模型的参数表沿用，起不来（专属禁键门 fail-closed 拒起）或行为
异常。

**根因**：同一基座换形是 env + boot 驱动的事，不是另找一套栈。参数表能不能沿用
是三段论：**别的模型的形不行**（专属禁键门）/ **别的引擎不行**（命名空间不同，
只有值可参考）/ **只有本模型自己那套形参数可行且值基本在册**。形态门是工具链
认不认这个模型的判据：启动器会调形态 lint，未知形态一律 fail-closed 拒起。

**判据**：换模型前核"权重身份三件"：**分片数 + `config.json` sha256 前 16 +
总字节**，逐项对注册卡（`deploy/models.d/` 一类）。

**处置**：自建某模型的形时，**禁抄别的模型的专属键**；换模型后按 P2-11 四查 +
P9-2 warm 门重新验收。

## P9-5 缓存配额是 per-store 语义（× 层数），guard 只 warning

**现象**：用户说"改成两层 4G"，按字面配成每层 4 = 8 GiB/host，超出预期一倍；
且起栈没报警，于是认为没事。

**根因**：该类缓存配额是**每层（per-store）额度**：per-host = 值 × 层数（"两层
4G"指每层 2 GiB × 2）。而且这道 guard **只记 warning 不阻起**——"没报警所以没事"
的推理不成立。

**判据**：自己按层数乘完再对上限；起栈日志 grep 到 warning 与否不作为安全证据。

按层数算 per-host 总量再对上限：

```bash
awk -v v=<每层GiB> -v n=<层数> 'BEGIN{printf "per-host = %g GiB\n", v*n}'
```

**处置**：改配额先算 per-host 总量再动手。

## P9-6 判定扩容收益看"淘汰次数"，不看命中率

**现象**：按命中率评估，得出"放大 4 倍收益大概率测不出"——这条旧结论已被实测
推翻，它就是拿命中率当尺子的后果。

**根因**：冷启动期命中率必然低，命中率反映的是热身进度，不是容量够不够。

**判据**：实测每层 0.5→2.0（即 1.0→4.0 GiB/host）：**淘汰从 1000–2100 次/轮降到
累计 7 次**，稳态命中率 58.8%（冷启动）→ 99.6% 中位、多次 `reads=0`（全命中），
性能零退化，代价 1.5–3.3 GiB/机。容量够不够，看**淘汰次数是否趋零**。

**处置**：扩容后按淘汰次数复判；冷启动命中率低不是失败信号。

## P9-7 靴槽锁：单一靴槽，双靴按事故论处

**现象**：双靴（两次点火重叠）= 缓存互踩、容器对撞、统一内存超卖。

**根因**：四机是**单一靴槽**设计；锁是互斥，不是排队。

**判据**：点火一律走槽锁入口（本仓 `tools/boot-with-slotlock.sh` 包裹 boot 件），
**勿绕过**；锁被占时的三步定性见 P2-8。

**处置**：看到锁被占的 RED，**先查是不是别人（含开机自启，P2-9）点了火**，别急着
排查自己的改动。

## P9-8 停机窗会不会让助手失联，先看主链指向

**现象**：同一停机窗，有时辅助代理不失联、有时全失联。

**根因**：主链指外部 API ⇒ 不依赖本地引擎，靴窗不影响；主链指回本地引擎 ⇒
停机 = 失联。

**判据**：查代理配置的 UPSTREAM 指向（同 P6-4 的判据命令）。

一条命令看清主链指向（外部地址 = 不失联；指向本地引擎口 = 停机即失联）：

```bash
docker exec <网关容器> sh -c 'grep -n UPSTREAM_BASE /app/config.yaml; env | grep -i upstream'
```

**处置**：主链指回本地的，动手前必须预警，别让人以为卡死。

## P9-9 主链在本地引擎上时，跑量具 = 自己跟自己抢卡

**现象**：运维期间在跑量具，同时主链（辅助代理）也在用同一引擎，读数与响应
双双受扰，事后说不清谁影响了谁。

**根因**：同一引擎同一时间只有一份算力；量具与主链并发时互相抢卡（同 P5-15 的
机理，只是这次"另一方"是你自己的主链）。

**判据**（三条纪律，跑前核对）：①开跑前先说明"这段时间我会变慢"；②量具
**必须串行**，这期间不派子代理 / 不起并行任务；③报告里如实标一句"读数含主链
自流量，误差在噪声带内"。

跑量具前确认没有并行任务/子代理在打引擎（期望 CLEAN 或只剩当前串行的一个）：

```bash
ssh <H1> 'pgrep -af "sd_bench|gsm8k|qeval|needle" || echo CLEAN'
```

**处置**：别装作绝对干净的实验室读数。

## P9-10 权限不够 ≠ 没权限做（docker 组 nsenter 通道）

> **显著风险声明**：本条仅限**自有集群应急排查**参考；**任何生产环境不应保留
> 该通道**——它等效宿主 root，保留即常驻提权面。使用后应复核动作并考虑收敛
> docker 组成员资格。

**现象**：普通用户 `sudo` 需密码、polkit 拦重启，据此判"无权限动宿主"。

**根因**：权限是多通道的。若该用户在 docker 组里，可起特权容器 nsenter 进宿主
PID 1，以宿主 root 身份执行。

**判据**（先试通道，再下结论）：

```bash
ssh <USER>@<H1> 'docker run --rm --privileged --pid=host -v /:/host alpine:3.20 sh -c \
  "nsenter -t 1 -m -u -i -n -p sh -c \"id\""'
```

**处置**：排查"能不能动宿主"时第一动作试这条路，别只试 sudo/polkit 就下"无权限"
结论；结论里写清用了哪条通道与风险。别把这条通道固化进任何自动化。

## P9-11 调度死锁：复现即整栈重启，取证在重启前

**现象**：长稳数十小时后 `#running-req` 冻结 + GPU 利用率归零 + 无新日志，随后
900s 量级 NCCL watchdog 四机同崩。

**根因**：引擎步级隐含宿主同步累积（上游修复方向）；判别读法、取证包与修复线
状态见 `docs/deploy/DEADLOCK-MITIGATION-AND-FORENSICS-20261018.md`。

**判据**（崩溃/重启前按序采集）：

```bash
docker exec <CTN> py-spy dump --pid 1
# 栈顶落在索引器数据构造（如 scoring/索引器取数函数）= 本死锁形（宿主同步等待）；
# 栈顶落在 ncclCommInit*/ncclLaunchKernel/allreduce 入口 = 通信初始化/链路面（另案）
ethtool -S <IFACE> | grep -E 'rx_|tx_' | head    # 有流量计数=曾开工后停滞；全零=从未开工
```

四机各采一份并对齐时间戳。

**处置**：**复现即整栈重启**（同参面重启后未复现是多站点一致事实）；**别单机
重启**（TP4 全环锁死，单机重起会卡 NCCL 握手）；watchdog 期内**别反复探测**
（dump 阶段额外请求只加噪声）。

# 十、生成质量面

前九章都在管"栈对不对、数准不准"；本章管**输出内容本身**的退化——栈完全健康，
内容也可能退化，而且退化点常常不在本栈。

## P10-1 思考流重复退化（"hmm" 循环）

**现象**：模型的 reasoning/thinking 流出现**固定短语循环**（如 "hmm" 等填充词
反复出现）。外部站点实测一次长会话：216 个思考块中填充词出现 **16150 次**，单块
最高密度 **10.5%**；且逐 token 间隔稳定（40-80ms 平稳节拍）——是**生成态**，
不是回放或重试残迹。

**根因**：这是**模型固有退化**，触发条件是三件事叠加：模型缺省采样参数 =
temperature 1.0 / top_p 1.0 / 无重复惩罚（`generation_config.json` 实读）+
超长上下文（>300-400K cached）+ 高 reasoning effort。**本栈引擎/网关不注入、
不改写任何采样参数**——serve 九参谱（`deploy/SPEC6-SERVE-REF.md`）里没有采样键，
网关注入面（P6-6 同一处）也不含采样改写，可据此自证清白。

**判据**（先分模型面还是引擎面）：

- **指向模型面**的三条同时成立：①退化只发生在思考流而**正文正常**；②填充词
  密度随上下文增长（越长越密）；③token 间隔平稳 40-80ms（稳定生成节拍）。
- **才查引擎面**的反指：①退化与特定 boot 形绑定（换形复现/消失）；②质量门
  同步红（GSM8K / qeval 口径见 `tools/bench/README.md` §4-§5）；③正文也坏。
  三者任一出现，先按引擎面排查，别直接归给模型。

**处置**（都在客户端侧，本栈不改）：

- 客户端显式发 **temperature 0.5-0.7（勿超 0.7）+ top_p 0.95**；
- 长会话加 **frequency_penalty 0.3-0.5**；
- 上下文 >300K 或单 turn 思考 >50K 字符时**降 reasoning effort**；
- 配超时/中止，别让循环吃满预算（同 P5-14 的 max_tokens 预算纪律）。
- 检测口径（可做成巡检）：**滑窗填充词密度**（>20 次/千字符告警）+ **4-gram
  重复率** + **连续同短语 ≥5 次**。

**别做**：别先动引擎参数/重启栈去"治"它（栈面无病灶）；也别在网关侧静默改写
用户的采样参数——那会把问题藏进栈里。
