## 0. 这套栈是什么（三句话版）

1. 这是一套把 DeepSeek-V4.1-Flash 大模型摊到**四台 NVIDIA DGX Spark（GB10 芯片，
   CPU 与 GPU 共享同一块统一内存）**上、用 **TP4 张量并行**当成一台推理服务器来伺服的
   全栈交付：模型、镜像、脚本、配置、量具都在这一个仓库里。
2. 推理引擎用的是开源 **SGLang**，但本仓的核心价值是在引擎外面加了一层**自有
   adapter/overlay 优化层**（通信、KV 显存、调度），并用一份几十键的 env 文件
   （现役 0.3.4 面 61 键）加八个 serve 参数把整个栈的形态**钉死成逐字节可复核、
   可回退的定版**。
3. 四台机器之间用 **RoCE 网络**互联，历史上存在两种物理形态——0.3.1 代的四口环网
   （历史）与 0.3.2 起的双口交换机（0.3.2/0.3.3/0.3.4 现役均为交换机形）——
   **两代形态不可混拼**，动手前必须先分清你的硬件是哪一种
   （分辨方法见本文 §2）。

入门路线：先把本文读完（约 30 分钟），术语随查用
[GLOSSARY-PUBLIC.md](GLOSSARY-PUBLIC.md)，然后按 §4 的学习路径图进入你要去的那条链。

## 1. 五个必须先懂的名词

### 1.1 形三元组

一句话定义：一次"可启动、可判读"的完整配置身份由三个面共同构成——**env 键面**
（一份环境变量文件，现役 0.3.4 参考 61 键、0.3.2 历史形 56 键）+ **serve 参数**
（引擎命令行参数谱，现役 0.3.4 面为八参）+ **adapter/overlay 面**
（注入引擎的自研优化件与覆盖上游的影子文件）；任何一次改动都必须让三个面**同一批次**
对齐，少一面就不成立。
为什么存在：为了让"这台机器上到底跑的是什么"可以被指纹化（md5/digest）、逐字节复核、
并且随时整体回退，而不是靠记忆和注释猜。
不懂它会踩什么坑：只换其中一个面（例如换了新镜像却沿用旧 adapter）栈照样能起、请求
照样能答，但修复被静默回退、读数悄悄漂移，你很难把症状归因到真正的原因。

### 1.2 adapter

一句话定义：adapter 是在容器启动时注入 SGLang 进程的自研优化件集合（装配后约 87 个
运行时文件），通过 `sitecustomize.py` 这个"装载缝"在 Python 启动的第一时间挂进去，
承担 KV 显存压缩、调度、通信钩子等全部本仓自研优化。
为什么存在：这样可以把优化层做成不改上游源码、可整树替换、逐件 md5 对账的独立资产，
上游引擎升级时优化层不必跟着改源码。
不懂它会踩什么坑：**adapter 与引擎镜像是绑定的**——只换引擎不换 adapter（或反过来）
都能起栈，但会静默回退上游修复，长稳与位级一致性会出问题；判读期内切面会作废读数
（见 [UPGRADE-0.3.2.md](../UPGRADE-0.3.2.md) §5 绑定律）。

### 1.3 overlay 影子挂载

一句话定义：overlay 是放在宿主机一个目录里的 29 个上游同名源码文件（0.3.2 历史形
为 28 件），boot 时被逐个
"影子挂载"进容器、盖住镜像里的原文件，从而在不重打镜像的前提下修正上游行为。
为什么存在：让对上游的小改动保持可审计（每个文件有 md5、四机全等可断言）、可回退
（换回旧目录即可），也方便与上游版本逐件对表。
不懂它会踩什么坑：影子目录是旧版时会**把新引擎盖回旧的**——栈照常运行，你以为在测
新版本，实际跑的还是被覆盖的旧代码（见
[PITFALLS-AND-FAQ.md](PITFALLS-AND-FAQ.md) 启动面 P2-2）。
仓内入口：29 件本体快照=[deploy/overlay/o12c1-prod/](../deploy/overlay/o12c1-prod/)
（自验 `cd` 进去后 `md5sum -c ../../prod/overlay-md5.txt`），平铺名→容器路径映射=
[overlay-map.tsv](../deploy/overlay/o12c1-prod/overlay-map.tsv)，对表清单=
[overlay-md5.txt](../deploy/prod/overlay-md5.txt)；每件的身份/md5/代际血统/旧形
去哪取，查备查区总表 [deploy/README-说明.md](../deploy/README-说明.md)。

### 1.4 engram

一句话定义：engram 是从模型权重派生出的 8 个分片的大体量预计算工件（合计约 189G，
按四机秩位分发），属于宿主机生成物，**boot 前置检查发现缺分片会直接拒起**。
为什么存在：把最耗时的权重预处理工作从每次启动挪到部署期一次完成，属于"用磁盘空间
换启动确定性"的设计。
不懂它会踩什么坑：换了新版权重却没有配套的 engram 分片（或分片与权重代次不符）时，
boot 拒起不是脚本坏了，是预期的前置门在工作，不要绕过它（生成与校验工具见
[UPGRADE-0.3.2.md](../UPGRADE-0.3.2.md) §4）。

### 1.5 靴槽锁与沉降

一句话定义：**靴槽锁**是保证"四台机器作为一个整体、同一时刻只允许一个 boot 流程"
持有的文件锁（点火脚本必须经锁包装器转起）；**沉降**是拆掉旧栈到点燃新栈之间强制
等待至少 600 秒的纪律。
为什么存在：四机是单一资源，两个会话同时点火会互相清缓存、容器对撞；旧栈刚拆完时
内存与页缓存还没回落，立刻点火会读到被污染的读数。
不懂它会踩什么坑：点火脚本返回码 2 常常不是启动失败而是**锁被别人占着**，先查锁文件
再排查引擎；不等沉降就开量，首档读数会系统性偏低（见
[PITFALLS-AND-FAQ.md](PITFALLS-AND-FAQ.md) 启动面与 [DEPLOY-GUIDE.md](DEPLOY-GUIDE.md) §7）。

## 2. 两代形态对照（先判断你的硬件是哪一种）

本仓同时保留两代网络形态的档案，同一个键在两代里取值不同、互不通用：

| 对照项 | 0.3.1 环网形（历史） | 0.3.2 起交换机形（现役，0.3.4 同形） |
|---|---|---|
| 物理拓扑 | 四台机用网卡口两两直连成环，**没有交换机** | 每机两块网卡的各一个口上联**以太交换机**（双 rail） |
| 每机 RoCE 口数 | 4 口（两卡的两个口全用） | 2 口（部署对） |
| 对向数据怎么走 | 中间两台机的网卡硬件转发（hairpin 规则） | 交换机直接转发（C 层 flat/one-shot 运行时） |
| 标志性 env 键 | 逐秩对端口映射表（PEER_HCA 一族） | 拓扑选择/扁平运行时/流量类三个交换机键 |
| 参考部署档 | [RING-DEPLOY.md](RING-DEPLOY.md) | [DEPLOY-STEP-BY-STEP.md](DEPLOY-STEP-BY-STEP.md) |

怎么判断你的硬件是哪种：最直接的办法是看机柜——四台机背对背网线两两直连、中间没有
交换机，就是环网形；每台机两条线上联同一台（或一对）交换机，就是交换机形。拿不准时
去 head 机数一下 RoCE 网卡口的使用数（4 口在役=环网，2 口在役=交换机）。

**不可混拼**：交换机键带进环网、或环网的逐口映射表带进交换机形，轻则启动被拒
（fail-closed），重则静默走错口对；两代只能整套切换，不存在"各取一半"。环网形
能安全拿走哪些 0.3.2 修复、哪些绝对不能拿，专档见
[RING-0.3.2-COMPAT.md](RING-0.3.2-COMPAT.md)。

## 3. 一个请求的生命周期

下面这张文字流程图给一个聊天补全请求从客户端到答案回传的完整路径，并标出
env/serve/adapter/overlay 各在哪一层生效：

```
客户端（OpenAI 兼容 SDK / curl）
   │  请求打到对外服务口（网关车道口，参考形 8001；8002=视觉车道，已撤除留回退线）
   ▼
并发代理网关（车道制分流：文本车道为主；鉴权、并发上限与背压、模型容量信息补全）
   │  （/v1/models 四键）
   │  网关自身不碰采样参数
   ▼
引擎回环口（生产口，参考形 8899；性能量具专用的测试口参考形 8898）
   │  ※ 引擎绑定两形态：公开 boot 件缺省 --host 0.0.0.0（四机可达）；
   │    参考产线形由站点收敛为只绑 head 机（rank0）的 127.0.0.1——
   │    后者的一切探活/量具都必须先 ssh 到 head 机上再打回环
   ▼
head 机上的 SGLang 服务进程
   │  此进程内同时叠着四层"形态"：
   │  · env 面：容器环境变量（boot 时由 ARM_ENV_FILE 指定的文件注入）
   │  · serve 参数面：进程 argv 里的八参（boot 脚本固定面）
   │  · overlay 面：影子挂载的上游同名文件（文件系统层盖住镜像内版本）
   │  · adapter 面：sitecustomize 装载缝注入的自研优化件（import 层生效）
   ▼
TP4 四机张量并行
   │  head=rank0 负责调度与拼装；三台 worker 各算四分之一张量
   │  机间经 RoCE 网络做集合通信（环网形走 hairpin 硬件转发，
   │  交换机形走交换机 flat 路径；b12x 通信树/NCCL 承载）
   ▼
生成 token 流按原路返回：引擎 → 网关 → 客户端
   （思考流与工具调用的解析格式由 serve 参数里的两个 parser 决定；
    写错 parser 名不报错，只会静默退化为纯文本——见 §6 第 4 问）
```

要点只有两条：第一，**探活与量具打哪个口取决于引擎绑定形态**（公开 boot 件缺省
`0.0.0.0`＝四机可达；参考产线形收敛为 head 机回环＝探活必须在 head 机的回环口上做，
在别的机器上 curl 回环不通是预期行为）；第二，网关与引擎是两个口、两层，量性能要
绕开网关（§6 第 10 问）。

这三样体积太大或受许可约束，**不进 Git、不随仓分发**——仓库里没有它们不是缺件：

| 大件 | 从哪来 | 怎么验身份 |
|---|---|---|

| 权重（模型本体） | 按模型发布渠道取得对应版次（现役参考形为 84 文件、约 476G；01/02 机本地、03/04 机走只读共享位；台账第 1 行 `.gitattributes` 缺失≠权重损坏，重建见 [WEIGHTS.md §1.1](../deploy/reconstruct/0.3.2/weights/WEIGHTS.md)） | 用仓内 SHA256SUMS 台账逐文件 `sha256sum -c`，84 行全过才算 |
| engram（预计算工件） | 宿主机上用仓内工具从权重现场生成（约 189G、耗时数小时），按秩分发到四机 | 对仓内 8 分片哈希台账逐件校验；缺件 boot 拒起 |

**digest 豁免判据（一句话）**：自行烘制的镜像只有在与发布完全相同的基座层链上才会得到
相同的 digest，换基座/换构建器得到不同 digest 时，以"逐件读回 md5 + 层数 + 单 COPY
层"作为内容判据，不要拿 digest 硬套——判据与操作见
[UPGRADE-0.3.2.md](../UPGRADE-0.3.2.md) §3。另有一个基线回滚点 tag 与配套恢复脚本，
把现役镜像固化成可整包下载的离线形态，见 [CHANGELOG.md](../CHANGELOG.md) 头部。

## 6. 常见第一周问题十连

**Q1：探活返回 000，是引擎死了吗？**
大概率不是，先分两步。第一步**认引擎绑定形态**（看 boot 件的 host 参数）：本仓公开
boot 件缺省 `--host 0.0.0.0`——引擎口四机可达，此时 000 多半是地址/端口写错；参考
产线形由站点把引擎口收敛为只绑 head 机的回环地址（127.0.0.1），你在跳板机或 worker
机上 curl 回环会得到 000（连接层失败），这是预期行为。第二步：回环形态下第一反应应该
是"我打错机器了"，先 ssh 到 head 机再打回环口。详见
[CALIBER-AND-MEASUREMENT.md](CALIBER-AND-MEASUREMENT.md) §0.1。

**Q2：镜像 digest 对不上，是不是拿到不同源的镜像了？**
不一定。同内容镜像在不同存储后端/显示口径下会给出不同形态的 ID（索引 digest 与
配置 digest 之差是已知现象）；判定的正法是**逐层哈希加内容判据**（层数、单 COPY 层、
逐件读回 md5），而不是只看一个 digest 字符串。详见
[PITFALLS-AND-FAQ.md](PITFALLS-AND-FAQ.md) 换装面 P3-2 与
[UPGRADE-0.3.2.md](../UPGRADE-0.3.2.md) §3。

**Q3：README 和各文档里那些 md5 是什么？**
那是"形指纹"：每个配置件（env 文件、adapter 逐件、boot 脚本）的 md5 就是它的身份。
用法是**一律实测对表**（`md5sum` 现算现比），不要看文件里的注释判断版本——注释会说
谎，md5 不会；改了注释文件 md5 就偏了，等于换了一形。详见
[PITFALLS-AND-FAQ.md](PITFALLS-AND-FAQ.md) 启动面 P2-10。

**Q4：我能只换引擎镜像、不换 adapter（或反过来）吗？**
不能。adapter 与引擎件是绑定的，必须同批切换：新镜像配旧 adapter 会静默回退上游
修复——能起、能跑，但长稳与位级一致性会出问题；只换 adapter 不换引擎同样不成立。
这是升级文档里标注"最高危"的一条纪律，见
[UPGRADE-0.3.2.md](../UPGRADE-0.3.2.md) §5 绑定律。

**Q5：env 文件最后一行怎么不生效？**
env 文件末尾缺换行符时，最后一行会被静默整个丢弃——不报错、不留痕。补上尾换行即可，
但注意补换行会改文件 md5，形指纹要同步重新登记。详见
[PITFALLS-AND-FAQ.md](PITFALLS-AND-FAQ.md) 启动面 P2-1。

**Q6：为什么我第一次测吞吐只有参考值的一半左右？**
你大概率交了"冷态税"：批次里最先跑的那一发会被系统性砸低（首靴未热、页缓存未就位），
实例中首档能低到正常带的一半以下。规矩是**每档至少三次独立调用取中位**，且塌陷点
每轮换位置时要看曲线单调性，别拿单发读数报回归。详见
[CALIBER-AND-MEASUREMENT.md](CALIBER-AND-MEASUREMENT.md) §3.1-§3.2。

**Q7：两代文档的表格里同一个键值不一样，听谁的？**
先认代际再对表：本仓同时保留 0.3.1、0.3.2 与 0.3.4 各代、环网与交换机形态的档案，同一键在
不同代里
取值不同是常态。动手前先确认手上这张表属于哪一代哪个形态，拿旧一代的表判新一代的
站，会把"做对了"判成"偏了"。详见 [PITFALLS-AND-FAQ.md](PITFALLS-AND-FAQ.md) 卷首一
与 [GLOSSARY-PUBLIC.md](GLOSSARY-PUBLIC.md) 的"代际"词条。

**Q8：模型思考流出现固定短语循环重复，是栈坏了吗？**
不是部署缺陷。这是已核实的**模型固有行为叠上未抑制的宽松采样**：思考链里出现口头禅
循环、正文却正常时，属于模型/采样面；缓解方法是客户端显式下发采样参数（温度、
top_p、重复惩罚）。判据与完整缓解清单见 [KNOWN-ISSUES.md](KNOWN-ISSUES.md)。

**Q9：守卫/门禁红了怎么办？**
先分辨红的是**通用门**还是**站点期望门**：通用门（md5 对表、横幅合同、env lint、
起栈接线闸门这类对任何站点都应成立的断言）红了，说明部署真的错了，按正档修；
站点期望门（warm 门阈值、水位地板、启动耗时健康带这类钉在参考站点硬件上的数值）
红了，先用同形基线复测——你的硬件可能合理地偏离参考值，应按自己站点校准后立门，
而不是硬"修"到与参考站一致。分层排查见
[PITFALLS-AND-FAQ.md](PITFALLS-AND-FAQ.md)，各参数含义见
[RUNTIME-PARAMETERS.md](RUNTIME-PARAMETERS.md)。

**Q10：我该用哪个口跑测试？**
性能量具（PR/DE/needle）一律打**引擎测试口**（参考形 8898），避开网关转发开销；
质量门（GSM8K/qeval）按各工具正典默认走网关口。最大的坑在默认值：主量具的
`--base-url` 缺省指向生产口，跑性能时必须显式改指测试口，忘了就会把压测流量打进
产线。详见 [CALIBER-AND-MEASUREMENT.md](CALIBER-AND-MEASUREMENT.md) §0.2。
